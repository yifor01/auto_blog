# Layer B 的 s2tw 對繁體不冪等——一句寫錯的文件註解讓生成端每天製造錯字

日期：2026-08-02
相關 commit：`9890372`（修復）、`2743bb0`（941 處回補）

## 問題

站上文章出現「PRISM2 的成功證明**瞭**「多模態對話」」。

不是孤例。掃過 `output/posts` + `output/blogs` 全 2029 個檔案：

- **47 個檔案**已被寫入 `證明瞭` / `說明瞭` / `表明瞭`
- 2026-08-01 當天生成的 23 篇裡有 **2 篇**中招
- 更廣義地：**650 / 2029 個檔案**只要再跑一次 Layer B 就會被改壞

而且這不是歷史包袱——它是**每天在產的新錯字**。

## Root cause

`CLAUDE.md` 與 `to_traditional_shape_only()` 的 docstring 都寫著：

> s2tw 無詞庫，對繁體輸入冪等。

**前半句對，後半句錯。** s2tw 確實沒有 TWPhrases（那是 s2twp 的東西，正是它把「文档→文件→檔案」
越轉越歪），但它仍帶 **TWVariants 的一簡對多繁分歧規則**。這些規則靠上下文挑分支，
對純繁體輸入照樣改寫：

```python
s2tw("证明了多模态对话")   # → 證明了多模態對話   ✅ 簡體輸入，正確
s2tw("證明了多模態對話")   # → 證明瞭多模態對話   ❌ 繁體輸入，改壞
```

**反直覺的地方**：簡體輸入反而是對的，繁體輸入才會壞。而 Layer B 的輸入正是
LLM 生成的繁中——它踩的永遠是錯的那一側。

全語料量到的 8 組（`difflib` 對齊、過濾掉真簡體後）：

| 誤改 | 次數 | 判定 |
|---|---:|---|
| 了 → 瞭 | 171 | ❌ 為了解決→為瞭解決、證明了→證明瞭 |
| 布 → 佈 | 235 | ⚠ 兩者皆通 |
| 只 → 隻 | 31 | ❌ 只是→隻是 |
| 局 → 侷 | 30 | ⚠ 兩者皆通 |
| 污 → 汙 | 29 | ⚠ 兩者皆通 |
| 表 → 錶 | 25 | ❌ 儀表板→儀錶板 |
| 制 → 製 | 14 | ❌ 定制→定製 |
| 回 → 迴 | 14 | ⚠ 混合 |

## 解法

### 逐段守門，而不是逐條列表

```python
def _gate_conversion(original: str, converted: str) -> str:
    parts = []
    for tag, i1, i2, j1, j2 in difflib.SequenceMatcher(
        None, original, converted, autojunk=False
    ).get_opcodes():
        seg = original[i1:i2]
        if tag == "equal" or any(_is_simplified_char(c) for c in seg):
            parts.append(converted[j1:j2])   # 含簡體 → 採納轉換
        else:
            parts.append(seg)                 # 純繁體 → 否決
    return "".join(parts)
```

一道守門擋掉全部 8 組，**零新增表項**。列表法要維護 8×N 條、且永遠追不完
（每個誤改字的脈絡都不一樣）。

成本：每篇約 8 ms（300 篇 / 50 萬字元實測）。Layer B 每天只跑 20 篇。

### 為什麼守門判準不能自己寫

三個看起來都對、實際都錯的判準：

| 判準 | 為什麼錯 |
|---|---|
| `t2s(seg) == seg` → 已是繁體 | 簡體字 t2s 後還是自己（`t2s('现')=='现'`），等於沒過濾 |
| `s2t(seg) == seg` → 已是繁體 | `s2t('干') == '幹'`，「受到干擾」會被判成含簡體而過門，接著變「受到幹擾」 |
| 自己列一份「繁體字表」 | 繁簡同形字（了/只/表/制/回/布/局）根本不在任何表裡 |

**正解是沿用專案既有的 `_is_simplified_char()`** —— 它做的是單字元探測
（`s2tw(ch) != ch`）**加上一張例外表** `_NOT_SIMPLIFIED_EVIDENCE`（`干托污`：
在繁體是正字，但單字元丟進 s2tw 就會變）。這張表早就因為 repair 層的同一個問題
存在了；本次只是發現 Layer B 也需要它，並補上「污」。

`_is_simplified_char` 原本呼叫 `to_traditional_shape_only()`，加守門後會遞迴回自己
→ 改用裸 converter（單字元不觸發 `_TERM_FIXES`，結果等價）。

### 存量回補的兩層阻擋

`output/posts` 正文有 657 處錯字（`引數` 474 / `擴充套件` 253 / `區域性` 63 / `繫結` 46），
而且**跑幾次 `repair-content` 都修不到**。兩個原因疊加：

1. `_repair_post_file()` 只改 frontmatter 的 `title:` 行，body 一律不動
2. 就算改了，`_clean_value()` 的簡→繁走 `_to_traditional_safe()`（**含簡體才轉**的守門），
   把 `_apply_term_fixes` 一起遮蔽了——這些詞只存在於純繁體正文裡，守門永遠不放行

修法：body 只做**定值錯字替換**（entity 解碼與簡→繁仍只限 `title:` 行，那兩者會改壞
程式碼區塊裡的 `&amp;` 與字串），並在 `_clean_value()` 補上 `_apply_term_fixes`。

## 可複用 pattern

### 1. 「不含 X」不等於「對已處理過的輸入安全」

s2tw「無詞庫」是真的，但那只排除了一類改寫，沒排除另一類。任何 s→t 轉換套在
已是目標語言的文字上，都要**實測冪等性**：拿一段純目標語言餵進去，看它動不動。

文件宣稱冪等時尤其要驗——這句話寫下的當下可能是對的，換一個 profile 或升一版就不是了。

### 2. 選擇性採納轉換：difflib 對齊而非逐字對位

想「只採納部分轉換結果」時，直覺是 `zip(original, converted)` 逐字比對。
**一旦有插入/刪除（詞替換改變長度）後面全部錯位**，跑出「n → 空白」「o → e」
這種一看就荒謬的結果。一律 `difflib.SequenceMatcher(..., autojunk=False)` 拿 opcodes。

`insert` opcode（原片段為空）該否決還是採納，要按語意決定——字元級對映的轉換器
不該憑空長出字，所以本例一律否決。

### 3. 測試的「前提斷言」不能用被測系統自己證明

修好之後 7 個既有測試同時紅，但**沒有一個是回歸**。它們開頭都有一句：

```python
# 前提：不擋的話這段真的會被改，否則本測試是空砲
assert to_traditional_shape_only(text) != text
```

這句話同時讓被測函式扮演「壞掉的參考實作」與「被測對象」。上游修好的那一刻，
前提恆為 no-op，主斷言就算刪掉守門也照樣通過。

改用繞過守門的最底層原語（`_raw_s2tw()` = 裸 `OpenCC("s2tw").convert`），
並在 docstring 寫明它為什麼繞過。

**判準**：如果我把生產程式碼修對了，這條前提會不會變成恆真？會的話它就守不住東西了。
而且是**靜默**失去——修好那天它會以「測試紅了」的形式出現，很容易被誤當成回歸而改壞。

### 4. 定值替換的誤傷面要從語料枚舉，不是想像

`引數→參數` 看起來人畜無害，直到掃到：

> 該獎項每年**吸引數**百款產品參選 → 每年吸參數百款

「動詞＋引」＋「數」會自然拼出 `引數`。改用 `_YINSHU_RE = re.compile(r"(?<![吸牽指索援])引數")`。

這條 bug 在 Layer A/B 一直存在，只是純繁體欄位從沒被套過所以沒落地——**擴大套用範圍時，
先跑一遍「新範圍裡這條規則會改到什麼」，不要只驗它會修對什麼**。

順帶：這是本專案修正表第一次用 regex，證明 regex 條目能與定值表並存且不破壞冪等。
`賽道里→賽道裡` 那批「需要負向前瞻」的候選從此不再是技術限制。
