## 問題一：版本上限鎖在 minor，擋不住 patch 版換字典

### 症狀（沒有症狀，這正是最麻煩的地方）

沒有任何報錯、沒有測試變紅、CI 全綠。前一夜的 status.md 記的是「1.4 改了轉換字典，已 pin `opencc<1.4` 止血，但該不該升未定」。

### Root cause

**`<1.4` 從一開始就沒鎖住該鎖的東西——1.3.2 就換了字典。**

1.3.2 的 s2twp 詞庫新增 `B超 → 超音波`（醫學 B 型超音波），且**沒有詞邊界保護**：

| 輸入 | 1.3.1 | 1.3.2 / 1.4.1 |
|---|---|---|
| `753B超大参数` | `753B超大參數` | `753超音波大參數` |
| `70B超越了GPT-4` | `70B超越了GPT-4` | `70超音波越了GPT-4` |
| `8B超轻量模型` | `8B超輕量模型` | `8超音波輕量模型` |
| `参数量7B超过预期` | `參數量7B超過預期` | `引數量7超音波過預期` |

`7B`/`70B`/`405B` 是 GenAI 語料最核心的術語形狀，後接「超大／超強／超越／超輕量」是極自然的中文搭配。而且**不可逆**：`753超音波大` 無法反推原本是 `B`，事後補救只能靠 regex 猜「數字+超音波」，是脆弱的。

`s2tw`（Layer B，無詞庫）不受影響——再次印證「兩層刻意用不同 profile」的設計。

### 為什麼一直沒被發現

**本機 venv 停在 1.3.1**（裝了就沒再更新），而 `daily-pipeline.yml` 每天 `pip install -e .` **無鎖版**。本地測試永遠綠，生產環境卻在裝別的版本。

這是「本地舊版剛好能過、CI 裝最新就紅」的變體，而且更陰險——**它不會紅，只會讓輸出悄悄變質**。

### 解法

1. 上限收到 `<1.3.2`（實測安全的確切版本）
2. 新增 `constraints.txt` 鎖 50 個套件的確切版本，三個 workflow 全改 `pip install -e . -c constraints.txt`
3. **把「為什麼鎖這個版本」寫成會紅的測試**（`TestOpenCCVersionGuard`）——餵 `753B超大参数` 斷言輸出不含「超音波」。裝錯版本立刻紅，而不是靜默漂移。

1.3.2 確實改對的部分（`想象→想像` 46 處、`市場營銷→市場行銷` 6 處、`臺積電→台積電` 4 處）改用修正表條目在 1.3.1 上收割——**拿走改善、避開退步**，比整包升版可控得多。

### 可複用 pattern

> **資料型依賴不跟 semver 走。**
> 轉換字典、斷詞詞庫、模型權重、規則表這類「行為由資料決定」的依賴，patch 版換整份表是常態。對它們設版本**範圍**等於沒設，要鎖**確切版本** + constraints 檔。
>
> **並且：為版本上限寫一條會紅的測試。** 只在 pyproject 寫個數字 + 註解，下一個人（或下一個你）會覺得「應該可以放寬吧」。把踩過的坑變成斷言，理由就不會流失。
>
> **驗證環境必須乾淨重建。** 長期存在的本機 venv 會讓你驗到一個生產環境根本沒有的版本組合。

## 問題二：變體修正表只能補歷史，生產路徑每天在重犯

### Root cause

`_VARIANT_FIXES`（修 OpenCC 一簡對多繁挑錯分支）只住在 `repair.py`。而 `repair-content` 是**修歷史**的工具，`to_traditional()` 才是所有新資料的必經路徑——於是每天的 pipeline 持續產出 `更復雜`／`死衚衕`／`剋制`／`臺積電`，然後等著下一次人工跑 repair 去補。

41 條實測有 **28 條在 Layer A 路徑真的會觸發**。

### 解法：搬家 + 守門

表搬到 `src/utils.py`，Layer A 與 `repair.py` 共用一份（各留一份必然漂移）。

**關鍵決策：Layer A 套用時帶「輸入含簡體字」守門**，這推翻了 status.md 原本記的「無條件套用」建議。

論證：本表修的是「**轉換過程中**挑錯分支」，這種錯只可能發生在真的被轉換的文字上。沒被轉換的文字套這張表，**只有誤傷、沒有收益**。實測無條件套用會改壞的正確繁體：

```
託馬斯 ← 「董事會委託馬斯克主導這項收購案」→ 委托馬斯克   ← AI 新聞高頻，最危險
係統化 ← 「把關係統化條列出來」          → 把關系統化
剋制  ← 「五行相剋制衡的道理」          → 相克制衡
穀底  ← 「稻穀底部的含水率」            → 稻谷底部
曆史  ← 「農民曆史上首次數位化」         → 農民歷史上
總檯  ← 「把總檯帳搬到雲端」            → 總臺帳
一齣來 ← 「看完這一齣來評論」            → 這一出來
```

### 兩種守門判準的取捨（有數據）

| | 判準 A：輸入含簡體字 | 判準 B：OpenCC 真的改變了文字 |
|---|---|---|
| 7 個誤傷反例 | 全部擋住 ✅ | 全部擋住 ✅ |
| `他很克制` / `20年谷底` / `更複雜的死胡同` | ❌ 修不到 | ✅ 修到 |
| `委託馬斯克撰寫文檔` | ✅ 安全 | ❌ **改成 `委托馬斯克`** |

判準 B 多修 3 個 case，但會**引入新錯**；判準 A 只是**沒修好舊錯**（那 3 個 case 在搬表前本來就是這樣）。

**選 A。** 依據是專案在簡繁修正上的一貫原則：**寧可少修也不要造新錯**。

已知代價的實際範圍很小：只要欄位裡有**別的**簡體字撐著守門就會放行並修對，而量子位／ChatPaper 這類真實來源的 abstract 是整段簡體，必然如此（實測 `他很克制这个冲动` → `克制` ✅）。受影響的只有「純繁簡同形的短欄位」。

### 根因其實還在上游

`to_traditional()`（s2twp）被**無條件套在所有 `ContentItem`** 上，包含本來就是繁中的來源。上述所有張力都源自這個設計。正解是讓 Layer A 只對簡體來源生效，而不是繼續加修正表——這條寫進了測試的 docstring，留給下一輪。

## 量測方法論：兩個踩過的坑

### 坑一：拿 round-trip 回推當 ground truth

想量「Layer A 今天還在產什麼錯」，做法是拿已修乾淨的存檔繁體當 ground truth、`t2s` 回推成簡體再跑一次 Layer A、比對差異。

結果跑出 94 種字元對，最大宗是 `文件→檔案` 134 處——**全是假象**。

因為存檔的繁體本身就是 Layer A 的產物，回推再轉一次等於**對同一段文字套了兩次 s2twp**，而 s2twp 對繁體不冪等（`文档`→`文件`→`檔案`）。量測方法和受測對象共享了同一個缺陷。

> **拿「處理過的輸出」回推「原始輸入」當 ground truth，前提是那個處理可逆。** 受測路徑本身不冪等時，round-trip 的雜訊會蓋過訊號。

### 坑二：最小輸入驗證會假綠

改用逐條驗證後（用條目所修的正確形式回推最小簡體輸入），41 條分成「24 條會觸發／17 條不會」。

但其中 4 條分類是錯的：`历史` 單獨轉是對的，`27年历史` 才會因為「年历」詞組被改壞。**最小輸入丟失了觸發脈絡。**

補救：對判為「不觸發」的條目，再用語料裡的**真實脈絡片段**複驗一次，抓回 `穀底`／`合並請求`／`曆史`／`係統化` 4 條。最終 28 條，與獨立算出的收益數字吻合。

> **兩種都要跑：最小輸入證明條目本身有效，真實脈絡證明它在實際資料裡會被觸發。**
