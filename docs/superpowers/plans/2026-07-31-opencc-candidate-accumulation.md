# 簡→繁修正表候選自動累積（方案 A）

Status: **設計草案，待裁示後實作**
Date: 2026-07-31
前置: `docs/solutions/2026-07-31-opencc-version-pinning-and-variant-table.md`（OpenCC 鎖 1.3.1、`_VARIANT_FIXES` 進 Layer A）

## 問題

`_TERM_FIXES`(8) / `_VARIANT_FIXES`(41) / `_TYPO_FIXES`(60) 共百餘條**全部靠人工逐句判讀**導出。
成本極高（歷經 6 種量測法，前 5 種都宣告「0 錯字」後被下一種推翻），且覆蓋面被「當時語料裡剛好
出現過什麼」限死——新詞、新機構名、新的一簡對多繁分歧都要等到出事才發現。

目標：讓候選**持續累積**，把人工從「每次大掃除重新逐句判讀」降級成「定期審查一小批帶脈絡的候選」。

## 三條不可破的鐵則（沿用，出處 status.md Next Steps 第 1 項）

- **(a)** `_VARIANT_FIXES` 對 `repair` 是**一次性機會**（實跑後欄位變純繁體、守門不再放行，日後補
  的條目對已修資料無效），但對 **Layer A 持續生效** → **自動累積的價值在 Layer A 側**，機制的產出
  終點是 `src/utils.py` 的 `_VARIANT_FIXES`，不是 `repair.py`
- **(b) 寧可少修也不要造新錯**。不確定一律拒絕
- **(c) 驗收標準不可從自己的修法導出**。不得用「套用候選規則後 diff 前後」驗收

## 實測基線（2026-07-31 巡邏，7 天 1051 筆）

| 指標 | 數字 |
|---|---|
| 語料相異漢字 | 1999 |
| 建出的歧義組 | 39 |
| 未被三表覆蓋的「少數分支」出現次數 | 269 |
| 其中確認為真錯誤 | **13–15（約 5%）** |
| **假陽性率** | **90–95%** |
| 產出至少 1 個真候選的組 | 9–10 / 39（26%） |

**最重要的發現**：`回/迴`(26)、`复/複→復`(30)、`制/製`(21)、`布/佈`(19) 這幾組的少數分支**100% 是
正確用字**。「少數分支＝可疑」這個直覺在多數組上不成立，噪音主要來自**專有名詞**（阿里、周鴻禕、
松應科技）與固定術語（自迴歸、遞迴、復盤）。任何設計都必須以「大部分候選是誤報」為前提。

## 架構

**核心決定：無狀態掃描 + 有狀態裁決帳本**（推翻巡邏報告原本的 append-only 佇列設計）

`data/raw/` 每天都 commit 進 repo，所以掃描可以隨時對既有存檔重算，不需要每天寫佇列。這帶來三個好處：

1. **不必碰 CI**。原設計要寫 `data/review/*.jsonl`，但 `daily-pipeline.yml` 的 `git add` 白名單只有
   `data/raw/`、`data/scored/`、`data/bookmarks.json` 與三個 output 目錄——**Actions 產生的候選每天
   都會被丟掉，且無 log 無報錯**。這正是本專案反覆踩到的「靜默失效」形狀
2. **去重免費**。原設計把「佇列不去重會變成人工不想看的噪音牆」列為頭號失敗模式；重算的設計裡，
   已裁決的 pattern 天然被帳本濾掉，不存在累積
3. **可重跑**。OpenCC 版本升級或字表擴充後，直接重掃全部歷史，不必回頭清理舊佇列

```
                    ┌─ data/opencc/ambiguity-groups.json   （靜態，僅版本升級時重建）
                    │
data/raw/*.json ──► 掃描器 ──► 扣除三表已覆蓋 ──► 扣除已裁決 ──► 候選報告（markdown）
                    │                                  ▲                    │
                    └─ src/utils.py 三表               │                    ▼
                                                        │              人工審查
                                        data/opencc/decisions.jsonl ◄───────┘
                                             （append-only）                │
                                                                            ▼
                                                        核准者手動加進 _VARIANT_FIXES
```

### 檔案

| 路徑 | 性質 | 說明 |
|---|---|---|
| `data/opencc/ambiguity-groups.json` | 靜態，進 repo | 一簡對多繁的歧義組。**用完整常用字表建，不是只用語料出現過的字**（解冷啟動盲點）。檔頭記 `opencc_version`，與 `constraints.txt` 不符時掃描器拒跑 |
| `data/opencc/decisions.jsonl` | append-only，進 repo | 人工裁決紀錄。每行一個 pattern 的 accepted / rejected + 理由 + 反例檢查 |
| `output/opencc-candidates/{date}.md` | 產出，不進 repo | 給人看的候選報告 |

### CLI

```bash
python -m src.cli opencc-candidates                    # 掃最近 7 天
python -m src.cli opencc-candidates --days 30
python -m src.cli opencc-candidates --all              # 全歷史（版本升級後用）
```

零 LLM、純離線字串比對。7 天 1051 筆實測秒級完成，全歷史 118 天預估仍在分鐘內。

### 掃描邏輯

1. 讀 `data/raw/{date}.json`，取每筆的 `title` / `abstract` / `tags`。**掃描範圍是全部 source，不是
   只有 RSS**——巡邏實測發現中文 GitHub README 也會餵進 Layer A
2. 對每個歧義組，找「非多數分支」字元的出現位置，取前後 15 字脈絡
3. 扣除已被三表任一 key **完整字串**覆蓋的（`key in text`）。
   ⚠️ **不可用單字元子字串比對**——巡邏過程中這個 bug 讓所有候選都被誤判為「已覆蓋」
4. 扣除 `decisions.jsonl` 已裁決的 pattern
5. 依 pattern 聚合：出現次數、**跨幾篇文章、跨幾天**、最多 5 則脈絡
6. 依「跨文章數」而非「總次數」排序——同一篇文章重複 10 次的價值低於 3 篇各出現 1 次

### 候選報告格式

```markdown
## `髮` (发→發/髮 組，少數分支)

- 出現 3 次，跨 3 篇文章，跨 2 天
- 建議：`髮` → `發`
- 脈絡：
  1. [2026-07-28 rss] ...這項技術是怎麼**被髮明出來**的，關鍵在於...
  2. [2026-07-29 blog] ...老黃在會上**髮了**一段影片...
  3. [2026-07-30 rss] ...錯誤總是**髮生在**部署之後...
- ⚠️ 反例檢查（審查者必填）：本組正確用 `髮` 的情形 = ______
```

## 鐵則怎麼落地

**(c) 不循環驗證** —— 核准一條候選必須同時滿足：

1. **≥2 則脈絡且來自不同文章**（單篇多次不算）。巡邏候選中只有 #1 `發/髮`、#4 `合作夥伴`、
   #8 `幾週` 達標，其餘 7 條都只有單一脈絡
2. **反例檢查欄位非空**。審查者必須寫出「這個 key 字串在什麼情況下會誤傷」，寫不出來就不能核准。
   這是把「委託馬斯克 → 委托馬斯克」那類教訓變成流程強制
3. **外部來源交叉核對**（教育部重編國語辭典或兩個獨立繁中語料庫詞頻）。**不得只憑審查者語感**——
   巡邏 agent 已明確聲明它的 8–10 條候選是自己的語感判斷、鐵則 (c) 尚未滿足，所以那批候選是
   **初篩，不能直接 merge**

裁決紀錄格式：

```json
{"pattern":"髮→發","verdict":"accepted","contexts":3,"articles":3,
 "counterexample":"頭髮/理髮/髮型，故 key 需帶動詞錨定：被髮明/髮生/髮了",
 "external_ref":"教育部重編國語辭典 發/髮 條","date":"2026-08-05","opencc":"1.3.1"}
```

**(b) 寧可少修** —— 預設拒絕。有歧義、脈絡不足、反例寫不出來，一律 `rejected` 並記理由；日後同
pattern 再出現會被帳本濾掉，不再打擾人。

**(a) 產出終點是 Layer A** —— 核准者加進 `src/utils.py` 的 `_VARIANT_FIXES`（有守門），並比照現有
慣例補錨定與反例註解。同時要意識到：這條對**已修過的歷史資料無效**（守門不再放行），只對新資料生效。

## 人工負擔估算

以巡邏的 7 天 269 筆估，若不去重約每天 ~38 筆候選、真錯誤 ~2 筆。但**帳本會迅速收斂**：假陽性主體
是專有名詞（阿里、周鴻禕），第一輪裁決後就永久濾掉。預期穩態是**每週審查 5–15 個新 pattern**。

建議節奏：**每週一次**，不掛進每日 pipeline。

## 會怎麼壞

| 失敗模式 | 防線 |
|---|---|
| 歧義組表沒隨 OpenCC 升版更新，新歧義漏掉 | 表頭記 `opencc_version`，與 `constraints.txt` 不符時掃描器**拒跑並報錯**（不是警告） |
| 審查疲乏後不查反例就核准 | 反例欄位為必填，空值不得寫入 `decisions.jsonl` |
| 冷啟動：稀有字沒出現過就永遠進不了候選池 | 歧義組用**完整常用字表**建，不用語料觀察到的字 |
| 覆蓋判定重犯單字元子字串 bug | 用完整 key 字串比對；為此寫一條會紅的測試 |
| 帳本把真錯誤永久誤殺 | `rejected` 帶理由與日期；OpenCC 升版時整批標記為 `stale` 需重審 |

## 實作範圍（尚未動工）

1. `data/opencc/ambiguity-groups.json` 產生腳本（一次性 + 版本升級時重跑）
2. `src/opencc_candidates.py` 掃描器
3. `src/cli.py` 新增 `opencc-candidates` 指令
4. 測試：覆蓋判定用完整字串（防子字串 bug）、版本不符拒跑、已裁決 pattern 被濾掉、跨文章計數正確
5. `CLAUDE.md` 補指令說明

**不在範圍**：自動改表（永遠人工）、接進 daily pipeline（改為每週手動）、巡邏那 8–10 條候選的
merge（需先補外部交叉核對）。
