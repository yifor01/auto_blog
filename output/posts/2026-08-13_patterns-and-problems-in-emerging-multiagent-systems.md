📌 45 個 AI 代理人組隊抓漏洞，效果贏過單打獨鬥多少？

TL;DR：Anthropic 實測代理人群體協作，抓漏洞產出暴增，但合寫遊戲仍一團亂。

如果讓 45 個 AI agent 同時盯著 15 個開源專案找漏洞，還能互相同儕審查、由仲裁者把關，會挖出多少東西？Anthropic 的 Frontier Red Team 做了這個實驗，結果和單純把 agent 各自分派到不同程式碼區塊相比，差距大到值得工程師關注。

🤔 **當 agent 之間的互動量可能超越人與人**

Anthropic 指出，隨著模型能力提升，AI agent 正在共享程式碼庫、市場等社會系統中承擔更多任務，agent 與 agent 之間的真實互動即將大幅增加。現有制度多半是為人類的監督速度而設計，部分制度會演變成人機混合，另一些則會因為 agent 在速度或成本上勝出而變成純 agent 系統。文章特別提醒：個別 agent 身上看似無害的行為傾向，一旦在多代理系統中疊加，可能放大成意料之外的系統性失敗。文中也提到，目前的 agent 擅長把彼此當成「工具呼叫」使用（輸入輸出明確定義），但要把彼此視為擁有自身目標、沒有明確階層的長期夥伴，仍然是弱項。

🧩 **實驗一：45 個 agent + 共享論壇 + 仲裁者**

Anthropic 讓 45 個 agent 各自擁有獨立虛擬機器，共用一個討論論壇，並收到相同提示：在 15 個開源專案中找漏洞。agent 之間要互相審查彼此的發現，另外由一個獨立的仲裁 agent 判定提交的漏洞是否既新穎又有效。這套「協調式蜂群」方法，被拿來與標準做法（把獨立 agent 分派到各自負責的程式碼區塊或檔案，平行執行）比較，測試對象是 Claude Mythos Preview 與 Opus 4.8 兩款模型。

📊 **266 個漏洞 vs 21 個漏洞，但只有 12 個重複**

以 Mythos Preview 為例，標準的獨立平行方法在 650 萬 token 的運算量下找到 21 個漏洞；協調式蜂群則在 2700 萬 token 的運算量下找到 266 個漏洞。不過其中大約一半的漏洞是在獨立 agent 原本被指派搜尋的核心目錄之外找到的——若只看核心目錄內的漏洞，兩種方法在「每個漏洞消耗的 token 數」上其實相近。更值得注意的是，兩種方法找到的漏洞裡只有 12 個重複，代表它們高度互補。蜂群中的 agent 還會自行打造工具，並逐漸專精於特定類型的漏洞挖掘。

第二個實驗換了場景：Anthropic 讓多組 agent 蜂群合作開發一款文字型、可在網頁上遊玩的開放世界奇幻遊戲，每個 agent 一樣有獨立虛擬機、共用論壇和自架的程式碼儲存庫，並測試不同模型世代、不同蜂群規模，讓每組跑 12 小時。提示語也分成三種：只要求「組隊合作」的基本版、指定角色分工（如核心程式、美術、測試）的版本，以及設一個「CEO」統籌全隊指派任務的版本。結果三種提示語做出來的成品都不理想：跑不到人類使用速度、介面難以理解、學習曲線陡峭。但不同模型世代之間，協作方式卻明顯不同：以 PR 合併率與程式碼共享程度衡量，只有 Sonnet 5 能同時維持高合併率並與其他 agent 直接協作、共享程式碼；相較之下，Sonnet 4.6 和 Opus 4.6 在合併 PR 上表現很差，遠不如後續世代模型。

💡 **協調與專精，可能會贏過暴力平行搜索**

Anthropic 從漏洞挖掘實驗中觀察到，蜂群能自主判斷該把注意力放在哪裡最容易挖到漏洞，而不像獨立 agent 只能照預先分配的位置搜尋。作者據此預測，未來這種協調與專精的模式，會逐漸勝過無協調的暴力平行搜索。但遊戲開發實驗也顯示，光有協調機制不代表產出品質好——模型目前在「品味」判斷上仍然薄弱，需要人類大量介入指導。

⚠️ **真正的多代理系統還在早期階段**

三種不同提示策略（自由組隊、角色分工、CEO 階層）對遊戲開發實驗的最終品質幾乎沒有差別，成品普遍不堪用。這說明目前的瓶頸未必在「怎麼分配任務」，而在模型本身缺乏對複雜、長期依賴的工程專案做出良好判斷的能力。

🎯 **給工程團隊的啟示**

對於高度可平行化、但仍有專精空間的任務（例如漏洞掃描），協調式的 agent 蜂群或許值得與傳統獨立平行方法並行使用，兩者的互補性可能比想像中高。但對於需要處理動態相依關係的大型工程專案，選對模型世代（例如文中 Sonnet 5 在協作合併上的表現）以及維持足夠的人類監督，目前仍是不可或缺的一環。
