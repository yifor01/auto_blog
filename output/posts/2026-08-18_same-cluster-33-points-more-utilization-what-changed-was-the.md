📌 同一座 GPU 叢集，只換了分配順序就多出 33 個百分點使用率

TL;DR：Dharma-AI 用 constraint-aware 分配器取代 FIFO 排程，同集群下 GPU 使用率最多提升 33 個百分點，價值最多提升 105%。

硬體沒有換，workload 也沒有換，唯一改變的是排程系統決定「誰先跑」的順序。這聽起來像是排程理論裡最無聊的一環，卻在 Dharma-AI 的實測中，把同一座 GPU 叢集的使用率拉出多達 33 個百分點的差距。

🤔 GPU 排程真正要回答的問題

文章開頭就把問題定義收得很窄：「把 GPU 用忙」不是一個系統可以直接執行的決策，真正要決定的是哪一顆 GPU、在哪一個時間格（timestep）、跑哪一個 job、給多高的優先權。形式化來看，這是每一組 GPU、job、timestep 組合的一個二元選擇，輸出是一張網格：每個 GPU 在整個排程區間裡，每一格要嘛填上工作名稱，要嘛留白。

四種工作型態會搶這張網格：訓練（training）、即時推論（real-time inference）、批次推論（batch inference）與量化（quantization）。它們可分成兩種分配形狀，難處也正好出在這裡：訓練、批次推論與量化屬於「批次型」，一旦啟動就需要一整塊連續 GPU，直到工作結束都不能中斷；即時推論則完全相反，是彈性的，跟著每個 timestep 變化的需求曲線成長或收縮。這兩種互不相容的形狀，要在同一個時間格裡搶同一批硬體，就是問題的核心。同一種工作類型內部也存在異質性：同一個基礎模型的訓練任務，可能短則幾小時、長則好幾天，用到的 GPU 數量也可能從一顆到數十顆不等。

🧩 FIFO 排程付出的兩筆代價

文章拿一個以 FIFO 為基礎的排程器當比較基準：即時推論吃固定保留額度，其餘工作一律按抵達順序放置，不考慮優先權。在叢集有餘裕的情況下，分配順序不影響使用率，不管先後順序反正都塞得下；但一旦進入資源競爭（contention），排序的代價就從隱形變成實際吃掉容量，而且分兩筆帳在算。

第一筆是「保留」的代價。即時推論等不了，GPU 必須在流量出現的當下就位，而 FIFO 排程沒有機制能在流量低谷釋放 GPU、再於下一波尖峰前收回，唯一能保證可用性的做法，就是把該應用一整天的尖峰需求量整天保留下來。文章舉例：一個中午需要六顆 GPU、凌晨四點只需要兩顆的應用，會把六顆 GPU 整整佔滿 24 小時，其餘四顆閒置卻無法釋出給任何批次工作。這正是為什麼在兩個以保留為主導因素的情境中，基準使用率會卡在半座叢集左右：混合情境 51.6%、訓練密集情境 53.6%。無論叢集是否真的擁擠，這筆代價都得付，擁擠只是讓它變得看得見。

第二筆是「順序」的代價。在真正的資源競爭下，哪些工作擠得進去，取決於放置的順序，而不只是總容量有多少。FIFO 依抵達順序放置每個工作，不衡量工作的價值，也不檢查後面還有什麼要塞進這個排程區間，結果就是高優先權的工作排在先抵達者後面等待，容量被用在後續工作根本用不到的位置上。這兩筆代價會疊加：為了應付單日尖峰保留下來的那塊 GPU，整天都不在批次佇列可用的選項裡，剩下的部分再依照抵達順序分配出去。

🧩 換掉排序邏輯之後

在五個為了製造真實資源競爭而設計的 benchmark 情境裡，新的分配器同時改善了兩個指標：使用率從 52%–85% 的區間提升到 72%–88%；優先權加權後的產出價值提升了 24.6% 到 105.1%，平均提升 52%。文章特別強調，五個情境、兩個指標，沒有一個要犧牲另一個來換。

其中最強的單一案例，是一個在 8 顆 GPU 上跑的訓練密集情境：使用率從 53.6% 提升到 87.0%，價值提升超過一倍，達 105%。分配器的做法，是把即時推論的需求當成一條會隨 timestep 變化的曲線去分配，而不是當成一個固定天花板，讓批次型工作填進需求的低谷，同時對即時推論工作在相鄰 timestep 之間能交換多少顆 GPU 設下硬性上限；批次型工作則改成依優先權在整個排程區間內統一排序，而不是照抵達順序處理。

📊 使用率相同，產出的價值卻差了 15.9%

有一個情境把「使用率」與「價值」這兩件事徹底拆開來看：在一個 64 顆 GPU、30 個工作的規模測試裡，FIFO 與新分配器的使用率完全相同，都是 44.9%，完成的工作數也一樣，都是 30 個裡的 27 個。但新分配器交付的優先權加權價值多了 15.9%。使用率只衡量「有多少 GPU 時間被用掉」，不衡量「用掉的時間產出的是什麼」，同樣的使用率、同樣的完成數，叢集實際產出的東西可以完全不同。

🧩 把問題寫成五條約束

文章主張，解法不是再疊加一堆 heuristic 規則，因為有些限制只有在「全域」層次才有意義，沒有任何局部規則能表達，例如連續區塊、整個排程區間內可接受的 GPU 調度總預算、正在執行的工作不能被搶佔的保證。因此問題被寫成一組完整的約束：每顆 GPU 每個 timestep 最多服務一個 job；每個 job 必須落在自己的需求範圍內，且已經在跑的工作會被繼承並持續保留；批次型工作佔用的連續 GPU 區塊，大小要是 2 的冪次；即時推論工作在相鄰 timestep 之間能交換的 GPU 數量有硬性上限；已經啟動的工作不能被中斷。

🎯 實務啟示

如果你的團隊管理的是一個混合訓練、批次推論與即時服務的共用 GPU 叢集，這篇文章給出一個具體的檢查點：先問自己的排程器有沒有把「即時服務的保留額度」當成一條會變動的需求曲線來處理，而不是固定天花板；再問工作是不是照優先權分配，而不是照抵達順序。這兩個問題的答案，可能比添購更多硬體更快改善叢集的實際產出。
