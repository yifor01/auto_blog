📌 openJiuwen X-Router:讓 Agent 自己學會「這次該找誰」,實測省下逾五成 Token

TL;DR：華為主導的開源 AI Agent 平臺 openJiuwen,推出可自我演進的模型路由引擎,實測成本大降逾五成而品質幾乎不變。

同一句「幫我把這句話翻譯成英文」,跟一道要通盤推演、寫五十行程式碼還要自己除三輪 bug 的難題,今天多數 AI 應用背後呼叫的,可能是同一顆、跑在最貴雲端算力上的模型。openJiuwen 團隊想解決的,正是這種「一個模型包打天下」的浪費。

🤔 **Agent 背後早就是一支隊伍,只是沒人排程**

現實裡,一個 Agent 背後往往同時握著本地模型、雲端模型,以及來自不同廠商的多種服務:有的推理能力強但貴且慢,有的輕快便宜但只能做簡單任務,有的擅長寫程式碼,有的多模態理解更好。當可選模型越來越多,新的麻煩也隨之出現——簡單任務用了昂貴模型造成不必要成本,複雜任務交給輕量模型導致效果不穩定,靠寫死的規則做選擇又很難跟上模型與業務的持續變化。openJiuwen 是由華為 2012 實驗室、華為雲、終端、計算、算力先遣隊等團隊,聯合高校與企業開發者共同構建的開源 AI Agent 平臺,這次給出的答案,是在 Agent 與模型之間加入一層面向請求的智慧決策能力——一個專門負責「這一輪任務該用哪個模型、用什麼策略」的路由引擎。

🧩 **三層架構:畫像、決策、自演進各自解耦**

整套路由體系拆成三層。第一層負責「看得準」,團隊基於歷史資料離線刻畫每個模型的能力畫像,並支援線上動態更新——當模型版本變動或表現發生變化時,畫像更新時延優於 1 分鐘,內容涵蓋不同任務類型與難度下的表現、延遲與功耗特性、成本量級,而不只是模糊的分數。第二層負責「選得對」,輸入除了當前請求的複雜度,還納入整條對話軌跡、KV 快取親和度(cache 命中與否可讓成本差出一截)、即時負載,以及目標模型是否剛超時或被限流;決策本質上是一個多目標最佳化問題,團隊的做法是基於候選模型能力、延遲功耗、使用者偏好等約束,構建啟發式最佳化演算法,選出「最優」而非「看起來最強」的模型。第三層負責「越用越準」,關鍵設計是狀態解耦:路由演算法是純函式,給定同樣的請求與狀態快照必須給出同樣的決策,不藏跨請求記憶也不帶隨機性;所有跨請求的歷史結果、排除項、快取親和、經驗資料,全部外接到獨立的狀態層;每次呼叫結束後,宿主把成功與否、耗時、成本等結果回報回狀態層,成為下一輪決策的輸入。這樣設計的好處是,狀態遺失時只會降級成「冷路由」,不會讓請求失敗;演算法升級也不需要動狀態層或宿主,而當樣本不足或優勢不明顯時,系統會保留原判定,不為了演進而演進。

📊 **PinchBench 得分幾乎持平,成本降 44.6%**

團隊把 x-router(目前落地的演算法模組,基於五檔複雜度分檔,支援端雲分級、本地能力邊界判斷、程序內小模型分類器,並用 Contextual Bandit 做經驗修正)接入 WorkSwarm,在 PinchBench 全量 147 個任務(涵蓋日誌分析、資料分析、編碼、研究等 11 個類別)上做了三組對比:全雲基線(全部呼叫 Kimi-K2-Thinking)、x-router 靜態路由,以及在靜態路由基礎上開啟 Bandit 自演進。結果如下:

| 模式 | PinchBench 得分 | 模型呼叫成本 |
|---|---|---|
| 全雲基線 | 71.36% | $11.11 |
| x-router 靜態路由 | 66.3% | $8.25 |
| x-router + Bandit 自演進 | 70.70% | $6.16 |

靜態路由比全雲基線得分低 5.1%,但成本降低 25.7%;開啟 Bandit 自演進後,成本較靜態路由再降約 25.3%,得分卻反而提高 4.4%。與全雲基線相比,自演進模式得分僅低 0.66 個百分點,幾乎持平,而成本從 $11.11 降到 $6.16,整體降低約 44.6%。團隊另在 Terminal-Bench/LLMRouterBench 上,用 Opus4.8/Qwen3.5-122B/Qwen3.5-35B 三檔位模型池做單輪與多輪路由測試:cost focused 模式下降成本 51.4%,成功率達 Opus 的 95.2%;quality focused 模式下降成本 15.7%,成功率達 Opus 的 98.6%。

💡 **省錢的關鍵不只是選便宜模型,是反饋閉環**

兩組實測指向同一個結論:成本降了四分之一到一半,品質卻幾乎沒退步,甚至在自演進模式下還回升。這代表省下來的成本,不是靠犧牲品質換來的,而是來自「不必要的強模型呼叫被篩掉了」加上「真實反饋持續修正路由判斷」。團隊也點出一個容易被純演算法視角忽略、但實際收益影響很大的因素:KV 快取親和度與即時負載,同樣的模型,快取命中與否、負載高低,成本與延遲都可能差出一截。

⚠️ **數字來自團隊自家評測,四個目標之間沒有萬能解**

以上 PinchBench 與 Terminal-Bench/LLMRouterBench 的數字都是 openJiuwen 團隊自行跑出的結果,尚未見獨立第三方複測。團隊也坦言,成本、延遲、品質、上下文/工具相容性之間本質上是沒有標準答案的多目標權衡,壓低成本品質可能崩、頂高品質成本可能失控,沒有一個參數能適配所有場景。

🎯 **實務啟示**

如果你的 Agent 系統已經同時接了多顆模型卻還在用寫死的規則或單一模型包打天下,openJiuwen 的「決策與執行分離」設計值得參考:路由層只管判斷、呼叫交給宿主執行,換演算法不用動骨架,未來新模型上線也不必重寫整套路由邏輯。專案已開源(Rust 核心、PyO3 提供 Python 介面),可透過 `pip install maturin && maturin develop` 搭配 TOML 設定檔快速接入既有 Agent。
