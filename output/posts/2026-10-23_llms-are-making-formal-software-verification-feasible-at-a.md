📌 Anthropic 與 Theorem 合作：用 Claude 把形式驗證做到組合語言層級

TL;DR：Claude 在 123 個開源函式庫的組合語言層級證明安全性，順道挖出陳年 bug。

寫 seL4 作業系統核心花了兩年人力，驗證它卻花了二十年人力——這個比例曾經是形式驗證（formal verification）之所以只留給 Airbus 航電程式碼這種頂級專案的原因。Anthropic 這次要說的是，LLM 正在把這道門檻大幅壓低。

🤔 **AI 既會找漏洞，也該被用來證明沒漏洞**

文章開頭點出一個現實：市面上大部分軟體都有 bug，而 AI 已經越來越擅長找出並利用這些 bug，傳統的防禦手段已經不夠用，我們需要能夠「證明程式碼沒有 bug」的方法。形式驗證正是提供這種保證的技術，但它歷來需要專家投入數年心力，讓大多數實務專案根本負擔不起。文章舉出 Linux 核心作為例子：即使是部署在數十億臺裝置上、經過最嚴密測試的軟體之一，最近仍被揭露超過 1,000 個漏洞。隨著前沿模型越來越擅長把看似無害的 bug 串成嚴重的漏洞利用鏈，業界需要能在漏洞被野外利用前就找到並修補它們的技術，理想狀況是能找到並修補所有 bug，然後證明再也找不到更多。

🧩 **形式驗證在做什麼：把程式碼變成數學模型**

形式驗證的做法是將程式碼轉換成數學模型，再嘗試證明它永遠遵守某組定義好的安全規則；如果證明失敗，就代表程式碼裡可能存在違反規則的 bug，而失敗的方式通常也能指出 bug 的性質；不斷重複這個過程（每次排除造成失敗的原因），最終就能得到「程式碼不含任何違反這些規則的 bug」的證明。問題在於，證明的規模往往遠大於原始程式碼，且需要高度專門的技能，這也是 seL4 案例裡實作花兩年、驗證卻花二十年的原因。

🧩 **把測試變成證明：從 fuzz test 到形式規格**

要證明軟體「正確」，第一步得先定義什麼是「正確」，也就是撰寫規格（spec）。有些程式容易定義規格，例如 PNG 解碼器可以依照 RFC 2083 定義其應有行為；但大多數程式——像文字編輯器或瀏覽器——很難說清楚「正確」是什麼意思，這正是大規模形式驗證的一大障礙。為了解決這個問題，Anthropic 的做法是把既有、可編譯的測試套件自動轉換成規格，編碼成「這組測試套件永遠會通過」的規則，並搭配一套通用的模型來描述任何 RISC-V 編譯二進位檔在 Linux 上執行的行為。具體流程可以拆成幾步：

1. 開發者原本就會為程式碼寫一個 fuzz test 的進入點（entry point），接收輸入，任何造成當機的輸入都被視為一個 bug。
2. Fuzzer（測試引擎）會在這個進入點灌入大量半隨機、經過變異的輸入，嘗試找出會造成當機的輸入；但這本質上是暴力搜尋，無法保證走過所有可能的程式路徑。
3. Anthropic 把 fuzz test 轉換成針對編譯後 RISC-V 指令的形式規格：這個規格宣稱，對於小於 64MB 的任何輸入，這個 fuzz test 都不會造成當機。
4. 如果 Claude 能證明這個規格成立，那麼針對這個進入點的 fuzzing 就變得多餘——因為已經被證明永遠不會再從這裡找到任何 bug。

這套流程被套用在 Google 的 OSS-Fuzz 計畫（為符合資格的開源專案提供持續 fuzz 測試，內含數千個開發者撰寫的測試進入點）下的數百個專案上。

📊 **123 個開源函式庫、組合語言層級的安全性證明**

Anthropic 表示，透過 Claude，他們在超過 100 個（文中具體數字為 123 個）真實世界開源函式庫上，於組合語言層級（RISC-V）證明了安全性質，這是他們所知第一次有人用 AI 大規模把形式驗證套用到組合語言層級的生產軟體上。具體來說，Claude 證明了這些程式在特定假設下（以單執行緒靜態二進位檔形式執行、固定記憶體預算、運行在 RISC-V CPU 的 Linux 作業系統上）一定會正常結束，不會觸發記憶體安全錯誤或斷言失敗——涵蓋小於 64MB 的任何輸入，以及任何被建模出來的 Linux 作業系統回應與記憶體佈局。更值得一提的是，Claude 在撰寫這些證明的過程中，發現了一些即使經過數兆次測試仍沒被抓到的陳年 bug。Anthropic 正在公開一部分證明，連同 RISC-V 與作業系統的語意模型，供外界驗證與重用；合作方 Theorem 也宣布願意為其他開源專案執行同樣的驗證流程，並發布一個 Claude skill 幫助開發者自行驗證程式碼。文章也提到，他們初步探索了其他形式驗證方法在別的安全任務上的應用，包括評估 zlib 壓縮演算法的安全性、證明一個用 Rust 寫成的 Python 解譯器的行為等價性，以及挖掘關鍵軟體中長年存在的 bug。

⚠️ **離「修完所有 bug」還很遠，但方向清楚**

Anthropic 坦言，這離修復所有可能的 bug還有很長的距離，但已經比過去更接近這個目標，並提供了一條可行的路線圖。隨著模型能力持續提升，撰寫證明的成本正在下降；而當越來越多程式碼被形式化、達成安全保證的方法越標準化後，證明在不同程式碼庫之間被重用或修改的能力，也會進一步分攤成本。

🎯 **實務啟示**

對維護有接上 OSS-Fuzz 的開源專案的工程師來說，這提供了 fuzzing 之後自然的下一步：如果 Claude 能證明某個 fuzz 進入點對應的規格成立，那個目標就等於被證明是安全的，省下的 fuzz 算力可以轉去覆蓋還沒被充分測試的路徑。文章也特別提醒，曾經用較弱模型嘗試過形式驗證、覺得「做不起來」而放棄的團隊，值得用現在的模型重新評估一次。
