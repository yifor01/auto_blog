📌 把 LLM 的記憶問題，交給 Datalog 解決

TL;DR：一名漏洞研究者意外把 LLM 記憶系統寫成程式分析引擎，用 Datalog 讓推論能增量更新、可追溯來源。

讓 AI agent 做幾小時的漏洞研究，最大的敵人往往不是它不夠聰明，而是它記性太差：你剛推翻的假設，它下一句還在用。

🤔 **告訴 LLM「這是錯的」，不代表它會停止相信所有依賴這個錯誤的結論**

作者長期用 LLM agent 協助漏洞研究，發現當一次調查拉長到幾個小時，模型就會逐漸失去對「目前已確立哪些事實」的掌握：它可能重新建議一個早就被排除的方法，忘記某個假設後來被證明是錯的，或是繼續拿一個已經失效的觀察結果來推論。市面上常見的記憶系統（把過去對話或觀察存起來、做 embedding、需要時取出相關片段）能存住「說過什麼」，卻無法保證模型「現在知道什麼」——如果某個中間觀察後來被推翻，舊記憶與新發現會一起被丟回 prompt，只能寄望模型自己想清楚哪些結論還站得住腳。

🧩 **這其實就是程式分析在解的問題**

作者從自己熟悉的程式分析工作中看出似曾相識的結構：程式分析通常有一組事實與一組規則，能從事實推導出新事實，並算出一個不動點（fixed point）；更重要的是，當某個輸入事實改變時，有成熟技術可以只更新受影響的部分，不必整個重算。這正是漏洞研究中缺的東西：當一個觀察改變，作者不希望 LLM 重新讀一遍整份對話紀錄、祈禱自己注意到所有連帶影響，而是希望「受影響的結論自動失效」。

這個想法後來變成 Lemmalog，一套給 LLM 用的 Datalog 引擎。它把問題拆成兩半：LLM 負責模糊、需要理解自然語言、原始碼與除錯器輸出的部分（例如把「LLDB 顯示這個已釋放的物件後來被當作寫入目標重複使用」轉成結構化事實），Datalog 引擎則負責從這些事實與規則中，確定性地推導出所有結論。舉例來說，若已知「攻擊者控制 object_a」「object_a 指向 object_b」「object_b 是核心物件」，規則就能推導出「攻擊者控制核心物件」；一旦「object_a 指向 object_b」這條事實被推翻，系統能精確知道哪些結論是依賴它推出來的，並自動作廢。

💡 **刪除一個事實，沒有想像中簡單**

作者遇到的第一個難題是「撤回事實」。新增事實很直觀，但刪除卻不然：如果某個結論 c 同時能從事實 a 推導、也能從事實 b 推導，刪掉 a 並不代表 c 要跟著消失，因為 b 仍然支持它；只有當 a 與 b 都被移除，c 才該真正消失。這在漏洞研究中很關鍵，因為一個結論常常有多條獨立的推導路徑（例如某個漏洞的可利用性，即使一條攻擊原語失效，仍可能透過另一條路徑成立），所以 Lemmalog 必須追蹤每個推導出的事實背後所有的支持依據，並隨事實變動即時更新。

這個追蹤機制順帶帶來一個額外好處：可以問系統「為什麼」。因為 Lemmalog 記錄了每個結論的推導鏈（來自哪些觀察、套用了哪條規則），使用者可以把一個像「candidate_3_is_exploitable」這樣的結論一路往下拆解到最原始的觀察紀錄。這也解決了作者在 LLM 輔助研究中常遇到的另一個惱人問題：模型有時會自信地說「我們已經確定這個指標是攻擊者可控的」，但實際上並沒有——只要在 Lemmalog 裡查不到這個結論的推導來源，就代表它根本不在被維護的知識狀態裡。

🎯 **實務啟示**

這個設計提供了一個值得參考的分工模式：讓 LLM 專心處理它擅長的模糊理解任務（讀懂自然語言、程式碼、除錯器輸出），把「維護知識一致性、追蹤依賴、增量更新推論」這類確定性工作，交給一個獨立的邏輯引擎去做，而不是每次都要模型自己在 prompt 裡重建整個推理狀態。這個思路不只適用於漏洞研究，任何需要長時間、多步驟且中途會推翻假設的 agent 任務（例如複雜除錯、根因分析），都可能用得上類似的架構。
