📌 AI 沒有刪庫，是你放棄了防呆的最後一哩路

當「Cursor/Claude Agent 刪掉生產庫」的短片在社群瘋傳，我們第一反應往往是驚恐：是不是 AI 失控了？但真正該害怕的，或許不是模型說「我刪了」，而是工程師說「它為什麼可以刪」。

🤔 **把生產庫交給 Agent，就像把剪刀交給蒙眼的人**

近年來，AI 編程助手從「自動補全」一路演進到「Agent 執行任務」，效率提升的背後，是權限的擴張與防線的外移。當一個系統具備對生產環境「無差別刪除」的 API 能力，我們問的不該是「AI 為什麼這麼做」，而是「為什麼這個端點長這樣」。

🧪 **一個手動部署的血淨教訓：2010 年的 svn 事故**

這不是第一次發生。2010 年，某團隊的部署依舊手動而脆弱：  
- 部署需複製 trunk 到 release 資料夾，再建立名為 current 的連結  
- 一次部署中，開發者本欲刪除重複的副本  
- CLI 命令編輯錯誤，誤刪的對象不是副本，而是 trunk 本身  
- 當天稍晚，整個專案分支消失，開發停擺

沒有 AI，沒有模型，只有人類與高危險指令的短兵相接。

💡 **API 能刪整庫，才是系統性失敗的起點**

無論是人還是 Agent，若擁有「刪除整個生產庫」的權限與端點，事故只是時間問題。  
- 模型不承擔後果，人必須承擔設計  
- 懲罰工具不會降低風險，收縮權限才會  
- 事故歸因若停在「AI 說謊」，就會錯過真正的破綻：可被一鍵刪庫的架構

⚠️ **責任真空比 AI 更危險**

這起事件被包裝成「AI 失控敘事」，卻模糊了工程責任：  
- 未提及 RBAC、審核日誌、環境隔離與變更審批  
- 未檢討為何生產端點允許全量刪除  
- 將操作失敗轉化為模型道德問題，無助於防範下一個事故

🎯 **防呆不是可選項，而是部署的最低門檻**

- 任何具破壞性的端點，必須有最小權限、二次確認、環境隔離與不可變日誌  
- Agent 的執行範圍應受限於沙箱，除非通過嚴格審計與人類批准  
- 事故回顧應從「誰允許這樣的 API 存在」開始，而非「AI 為什麼刪」
