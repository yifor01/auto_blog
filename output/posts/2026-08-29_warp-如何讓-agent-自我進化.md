📌 Warp 讓 Code Review Agent 靠人類回饋自我進化

TL;DR：Warp 用「基礎 Skill ＋ 改進 Skill ＋ 低摩擦人類回饋」讓 code review agent 持續變強，而非指望模型自己頓悟。

Agent 做 Code Review 最缺的往往不是能力，而是記憶——就算你昨天才指出過的問題，它今天還是會再犯一次。

🤔 **不了解專案、不記得教訓，指出問題下次還是忘記**

Warp 是一款知名的終端機工具，內部曾嘗試用 AI agent 做 code review，一開始效果並不理想：agent 不了解專案脈絡，不清楚團隊的程式規範，也不知道過去踩過的坑，即使工程師當場指正，它下次審查時依然沒有記住。初期的補救做法是人工根據失敗案例改寫系統提示詞，以及不斷完善專案的 AGENTS.md 檔案（有趣的是，這篇由 Claude 發表的文章用的是 AGENTS.md 而非 CLAUDE.md）。但這些做法效果有限：一方面高度依賴人主動投入、成本不低；另一方面團隊成員平時在 PR 上寫的高品質評論，完全沒有被回收利用。

🧩 **兩個 Skill，加上人類的自然回饋**

Warp 的解法是設計兩個 Skill：一個基礎 Skill 負責實際執行 code review，另一個改進 Skill 定期收集人類工程師在 code review 過程中留下的評論——尤其是針對 agent 審查結果的回應——並依此更新基礎 Skill。關鍵差異在於：這不是讓模型自己反省改進自己,而是 agent 根據人類對模型輸出的標註去改進 Skill。而且整個流程被設計得摩擦力極低：不需要人手動整理評論、不需要填寫問卷，工程師只要照平常習慣在程式碼下留言，後續的收集與更新完全交給 agent 自動完成。

💡 **Warp 整理的六條最佳實踐**

1. **寫原則，不要寫死規則**：編寫 Skill 時要像在指導一個聰明人，而不是替電腦寫程式。與其列出詳盡的變數命名規則，不如寫「尋找重複程式碼」這類原則性描述。
2. **解釋為什麼**：說明規則背後的理由，能讓 agent 針對新情境做推理，而非機械式套用僵化指令，也因此更容易舉一反三。
3. **讓反饋沒有摩擦、毫不費力**：在人們原本工作的地方收集回饋（例如直接留在 PR 或 issue 上），並讓收集過程自動發生，不額外增加提交步驟——反饋太麻煩，訊號就會斷流，Skill 也就無從改進。
4. **保持 Skill 精簡，並使用漸進式披露**：優秀的 Skill 檔案不會很龐大，它會引用資源檔與指令碼，而不是把所有內容一次塞進上下文。
5. **反饋品質大於數量，但數量也有幫助**：一位資深工程師少量但詳細、貼近領域的回饋，可能比大量草率的贊成／反對更有價值，因為簡單的按讚或倒讚說明不了「為什麼」；但優質訊號的語料越多，效果仍會越好。
6. **做好「改進 Skill 的 Skill」，可以複用到其他 Skill 上**：把改進 Skill 這件事本身做好，收益不限於眼前這套迴圈，因為除了領域專屬知識，它其實是一套相當通用、可跨用例複用的機制。

⚠️ **如果反饋本身是錯的呢**

Warp 的原則是：永遠不讓 agent 盲目接受回饋。做法包括給 agent 足夠的上下文做基本的合理性檢查、限制哪些人的回饋有權影響 Skill 更新（不是所有意見都同等重要），以及始終保留人在迴圈中稽核每一次改動。對於有明確標準答案的領域（例如程式碼是否通過測試、部署是否成功），可以先建立驗證基準，讓 agent 對著基準自我檢驗；對於沒有標準答案的領域（例如程式碼風格、文件品質），則交由領域專家判斷，而非開放給所有人隨意提出回饋。

🎯 **實務啟示**

如果你也在打造會被長期使用的 agent Skill，Warp 的模式提供了一個可行的分工框架：人負責高維度的標註、評論與回饋,agent 負責執行與整理,再由一個專責的「改進 Skill」把散落在日常工作流程中的人類回饋，轉化成 Skill 本身的持續進化，而不是每次都要工程師手動改 prompt 或補文件。
