📌 【OpenAI Blog】OpenAI 如何安全運行 Codex  

你以為讓 AI 幫寫程式只要把模型丟進 IDE 就能跑？OpenAI 卻在內部加了四層防護，才讓 Codex 能在生產環境中安全使用。  

🤔 **AI 編程的便利背後，安全風險在哪裡？**  
隨著 Codex 等程式碼生成模型被納入開發流程，未受控制的執行可能帶來資料外洩、惡意指令或供應鏈攻擊的風險。如何在保持開發者體驗的同時，確保代碼執行的安全與合規，成為團隊必須解決的問題。  

🧪 **四層防護機制：沙盒、核准、網路政策與遙測**  
OpenAI 內部採用了以下措施來降低風險：  
- **沙盒**（Sandbox）：將 Codex 產出的程式碼隔離在受限的執行環境中，防止對主機系統造成不可逆的影響。  
- **核准流程**（Approvals）：在程式碼才能進入沙盒前，必須經過人員或自動政策的審核，確保符合內部安全規範。  
- **網路政策**（Network Policies）：透過防火牆與出入站規則，限制沙盒內程式只能與特定內部服務通訊，阻斷未授權的外部連線。  
- **Agent‑native 遙測**（Agent‑native Telemetry）：在代理層級內建記錄與監控機制，即時捕捉執行行為、異常事件及資源使用情況，供事後審計與即時警示使用。  

 **沙盒＋核准＋網路政策＋遙測共築安全防線**  
這四層措施並非全新發明，而是將業界已知的安全最佳實踐（隔離、審核、網路分段、觀測）組合應用於 Codex 的代理工作流程。組合使用可以在不顯著增加開發者摩擦的前提下，提供深度防禦（Defense‑in‑Depth），使單一層失效時仍有其他層次可緩衝風險。  

💡 **每層防護的設計考量與實務取捨**  
- 沙盒選擇了輕量級容器或微VM，以啟動速度與資源隔離取得平衡。  
- 核准流程採用可設定的政策引擎，允許團隊根據專案敏感度調整審核嚴格度。  
- 網路政策採用「最小權限」原則，只開放必要的內部 API 端點，降低橫向移動風險。  
- 遙測則著重於低開銷的事件採樣與結構化日誌，方便與既有的 SIEM 與警報系統整合。  

⚠️ **內部最佳實踐，外部適用性尚待驗證**

🎯 **工程團隊可參考的安全採納指引**  
- 在引入程式碼生成代理時，先考慮執行環境的隔離程度。  
- 建立可自動化的程式碼核准政策，隨專案風險等級動調。  
- 以最小權限原則設計網路存取規則，並定期審閱。  
- 利用代理層的遙測資料，建置異常行為偵測與審計管線。
