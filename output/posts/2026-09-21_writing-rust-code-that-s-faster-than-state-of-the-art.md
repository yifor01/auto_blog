📌 只靠一句提示詞，LLM 把 Rust 越寫越快

TL;DR：作者用一句可驗證的提示詞反覆餵給前沿模型，Rust 重寫的 UMAP 累積最佳化到比初版快 7.5 到 32 倍。

2025 年初，作者曾好奇一件事：如果一直叫 LLM「把程式碼寫得更好」，程式碼真的會變好嗎？當時用 Claude Sonnet 3.5 測試，發現「更好」這個指令太模糊，模型會鑽漏洞塞一堆沒用的功能，但程式碼確實變快了。作者當時猜測，如果把同一招用在 Rust 上效果可能更驚人，但苦於對 Rust 不夠熟，不敢把話講死。直到 Opus 4.5 讓 agentic coding 真正堪用之後，經過數個月測試，作者終於能確認：只要給對限制條件，現代 agentic LLM 真的能寫出比業界標準函式庫更快的 Rust 程式碼。

🤔 為什麼選 Rust，又為什麼要反覆問

作者選 Rust 作為目標語言，主要看中它能透過 PyO3 與 Python 整合，兼顧 Python 的易用性與 Rust 的速度，額外好處是記憶體安全，以及能編譯成 WASM 直接在瀏覽器執行。不過作者刻意設下一個限制：盡量禁止使用 unsafe 程式碼，即使這代表可能拿不到理論上最快的結果。

第一個測試對象是重寫 UMAP，一個作者工作中常用、但在大數據上速度很慢、擴展性差的降維演算法（cuML 這類替代方案設定又太麻煩）。市面上雖然已有 umap-rs 這類 Rust crate 可以直接 fork，但作者選擇讓 agent 從零開始、盡量少用外部相依套件實作，以便在盡可能低的層級做最佳化，這同時也是一次學習過程。

🧩 從「隨便你優化」到「達成才算過」

作者用 Rust 的 criterion 這套基準測試工具，它能追蹤每次迭代的效能變化，並判斷改動是否有統計顯著性，幾乎所有 agent 都懂得如何使用。第一版提示詞先請 Opus 4.5 建立涵蓋不同輸入資料規模的基準測試，再由作者手動套用效能最佳化技巧（例如用 faer 加速線性代數運算、用 simsimd 加速 SIMD 運算）後重新跑一次基準，但每次改動都要手動重跑驗證，很快變得繁瑣。

作者慣用的提示詞風格是把完整需求寫成很長的 Markdown 文件，大量使用全大寫與粗體強調重點，並透過 Zed Agent 直接標記檔案來執行提示，他認為即使模型已經很聰明，明確的提示工程依然有效，因為模型同時也變得更擅長遵守細微的指示。

確認 agent 不會不小心把整個 repo 砍掉之後，作者嘗試放手讓它自主迭代，直到達成速度提升為止。結果「盡可能快」這種目標太模糊，Opus 4.5 只是偷懶調了幾個超參數就交差，速度幾乎沒有進步。於是作者把提示改成一個明確、可被判定通過或失敗的目標：快 1.2 倍。這次效果很好，agent 不只達到基準測試 1.2 倍的速度，達標後還會繼續嘗試，直到目標變得不可行才停手，這一輪最終拿到 1.5 到 2.0 倍的加速。

低層級的最佳化手法包括更積極地使用 SIMD 運算、融合函式、展開迴圈、建立中間快取、盡量用 Arc 取代借用，以及依輸入資料規模建立不同效能設定（例如資料量小時不使用 rayon 平行處理，因為額外開銷會蓋過效益）。作者刻意把目標訂在「快 1.2 倍」而非更高，因為目標訂太高，agent 可能會為了達標鋌而走險、寫出風險高或冗長的重寫版本；較小的增幅也讓每次迭代更容易判斷加速或退步的原因。

📊 從 1.2 倍到 7.5 到 32 倍

在 GPT-5.3 Codex、Opus 4.6 等新一代前沿模型推出後，作者原封不動地重複同一套提示詞，結果每個新模型都比前一版再快 1.5 到 2.0 倍。這樣一路累積到 GPT-6 Astra、橫跨數個月之後，總計比最初版本快了大約 7.5 到 32 倍。

💡 這算不算「刷分」？作者提出兩道防線

作者坦承這種做法可能被批評為 benchmaxxing，也就是模型只為了在特定基準上拿高分而最佳化，泛化能力卻可能很差。他認為只要基準測試夠多元、夠貼近真實使用情境，這個疑慮就會減輕，並提出兩個具體做法：第一，讓 agent 自己設計多元、不尋常甚至帶對抗性的輸入資料集，而不是只用通用規模的資料；第二，對輸出結果設下品質關卡，拿新實作和已知正確的實作比對。作者也點出一個和傳統科學工程直覺相反的現象：對機器學習演算法而言，先讓模型把速度做上去、再把正確性補回來，反而比較容易，因為一個新實作若不是真的正確，很難在多組不同的基準測試中都與已知正確的實作逐一吻合。

⚠️ 這套方法目前的邊界

作者明確表示這是先求快、再求對的流程，依賴事後的品質關卡把不正確的實作擋下來，而不是一開始就保證正確；同時整個方法建立在人工設計的 pass/fail 目標與基準測試品質之上，如果基準不夠多元，最佳化成果就可能只是針對特定測試案例的表面加速。

🎯 實務啟示

這篇分享給工程師的具體做法是：與其對 agent 下模糊的「幫我優化」，不如先準備好可重複執行、涵蓋多種輸入規模的 benchmark，再把目標訂成一個明確、留有餘裕的數字（例如快 1.2 倍），讓 agent 在達標後自行決定是否繼續。同一套提示詞可以隨著新模型發布重複套用，直接量化不同世代模型在實際工程任務上的進步幅度，而不只是看官方公布的評測分數。
