📌 【Anthropic 官方發布】用 Claude 自動化打造評測與逐步最佳化

TL;DR：claude-api skill 新增兩個指令，自動化建置評測與逐步最佳化流程。

你的 AI 應用到底有沒有變好，還是你只是在自己騙自己？Anthropic 這次把「怎麼做出一個不會騙人的評測」和「怎麼在不過度配適的前提下逐步改善」都寫成了 Claude Code 裡可以直接呼叫的指令。

🤔 **評測設計為什麼這麼難**

這篇文章指出，評測（evaluation）提供的是你的應用或 skill 在特定任務上的表現訊號，但設計評測、以及在不自我欺騙的前提下改善表現，其實不容易。常見的錯誤包括：為了方便生成或方便打分而選錯任務分佈、忽略任務本身的模糊性、或是評分者（grader）本身不穩定。

🧩 **好評測的四個共同特徵**

文章列出設計良好評測的四個要素：
1. 任務要能反映真實的生產環境使用情境，而不是因為好生成或好打分才被選中。
2. 更強的模型、更多的思考（effort）應該帶來更高的分數；如果沒有，通常代表任務本身有歧義，或評分者校準出了問題。
3. 在前沿（frontier）模型用最高 effort 時，分數也應該明顯低於 100%，否則無法可靠判斷後續改動的影響，而且這個差距不該是來自不可能完成或模糊的任務。
4. 同一設定下多次執行的變異（run-to-run variance）要低；高變異通常來自任務本身模糊、評分者對相同輸出給出不同判決，或是環境殘留狀態（例如前一次測試留下的檔案、git 歷史）洩漏了答案。

文章也特別點名「對抗性抽樣（adversarial sampling）」的陷阱：如果只挑「現在這個模型會答錯」的案例，等於只在取樣某一個模型能力曲面上的低谷，最後評測測的其實是這個模型的特定失敗指紋，而不是應用真正在意的難度。建議改成：挑選人類判斷確實困難、且能說明「為什麼難」的案例；納入從生產流量、bug 回報、工單中觀察到的具體失敗案例；但不能完全信任使用者流量，因為使用者通常只會嘗試他們預期會成功的操作，純靠使用紀錄取樣的任務分佈容易偏向過於簡單。

🧩 **/claude-api build-eval：讓 Claude 主持訪談、自動建置評測**

執行 /claude-api build-eval 後，Claude 會在對話中訪談使用者，直接在你的程式碼庫裡建出評測，並在特定節點暫停等待確認。取樣案例的優先順序依序是：生產環境的對話紀錄（會先詢問資料保留與敏感性問題）、bug 回報與客服工單、使用者手寫的 5 到 10 個案例，最後才是從程式碼庫合成的案例。

建好輸入案例後，Claude 會依應用的輸出型態提出最省錢的評分方式：如果輸出空間受限（固定分類、符合 schema 的 JSON、能跑測試的程式碼），就用程式化驗證（exact match 等）；如果輸出是開放式但有清楚的品質標準，就預設用 LLM-as-judge：由另一個模型讀取輸入、輸出和寫成「可檢查陳述」而非 1 到 5 分量表的評分準則，給出分數與理由；如果有基準（baseline）可比較，評審模型則會在不知道哪個是基準、順序隨機的情況下，直接選出較好的一方。使用者可以自行選擇評審用的模型，但規則是它不能是被測試的那個模型。Claude 會先手動評幾個案例，詢問使用者是否會打出不同分數，藉此校正評分者。

確認評分者沒問題後，指令會告知評測規模（案例數 × 重複次數 × 模型數）與大概花費時間，接著跑一次基準並附上信賴區間的分數。產出的東西包括：所有案例、評分邏輯、執行腳本、每個案例一行 JSON 加一份完整對話紀錄，以及一個列出每個案例分數並連到該筆對話紀錄的靜態頁面；如果想要更多呈現方式（例如圖表），只要提出要求 Claude 就會另外做一頁，而且這些額外頁面預設是純本地檔案，不會向外連網。

在跑基準的過程中，Claude 還會做幾項診斷檢查：對同一個輸出重複跑評分者兩次，確認判決是否一致；檢查是否有逾時、API 錯誤或被截斷的回答，避免把基礎設施噪訊誤判成模型表現的變異；如果基準分數已經高達 95% 以上，則會提醒使用者，此時逐步最佳化應該轉向探索成本或延遲，而不是繼續追求分數。

🧩 **/claude-api hillclimb：一次只改一個變數，用 held-out 集避免過度配適**

有了可信的評分方式後，下一步是 hillclimb（逐步最佳化）：調整像是 effort 或 prompt 這類會在成本與表現之間做取捨的參數，同時保留一組 held-out 範例來抓出過度配適。文章給出兩個選擇優化對象的原則：一是「便宜迭代」，優先選擇修改成本低、容易復原的介面，像是文字、prompt、skill 本身，而不是對 agent harness 做大範圍的程式碼改動；二是「可歸因」，分數的變化要能明確歸因到正在調整的那個介面上，文章提到多個成功案例都是把焦點放在 skill 的觸發邏輯（skill triggering）上。

🎯 **實務啟示**

對正在維護 Claude 應用或自訂 skill 的團隊，這套流程把「怎麼確保評測本身值得信任」具體拆成了可檢查的步驟（評分者一致性、基礎設施噪訊、headroom），而不是憑感覺相信一個分數。更實際的是，把 hillclimbing 限定在「便宜且可歸因」的介面（prompt、skill 觸發條件）上，而不是貿然大改 agent 架構，能避免把進步的訊號和噪訊混在一起。
