📌 350 億參數擴散語言模型殺進 Agent 戰場，中位執行時間比對手快逾一倍

TL;DR：擴散智慧發布 Clover-35B-A3B-Preview，用擴散語言模型做 Agent 任務，實測速度與成功率雙雙超越自迴歸對手。

擴散模型給人的印象一直是生圖、生影片的工具，沒想到這次它被拿來寫程式碼、操作網頁、呼叫工具,直接下場當 Agent，而且速度還比我們熟悉的自迴歸模型更快。

🤔 自迴歸模型的「詞語接龍」,碰上 Agent 任務的等待焦慮

我們熟悉的自迴歸（Autoregressive）語言模型是根據前文預測下一個 token，一個接一個生成，也就是常說的「詞語接龍」。這種逐字生成方式在需要反覆呼叫工具、根據回饋調整動作的 Agent 任務中,序列等待的時間成本會被放大。擴散語言模型換了一種思路：允許多個位置同時更新，再經過幾輪迭代逐步完善結果，理論上有機會減少逐 token 生成的等待。這次發布 Clover-35B-A3B-Preview 的團隊「擴散智慧」,由香港大學孔令鵬教授與其博士生龔珊三、葉佳成共同創立，其成員對擴散語言模型的探索可追溯到 2022 年提出的 DiffuSeq（研究如何用擴散模型做序列到序列文本生成），2025 年 4 月推進到 70 億參數的 Dream 7B，這次的 Clover 則進一步擴大到 350 億參數規模。

🧩 塊擴散＋重構 Gated Delta Network，讓歷史記憶與當下生成各司其職

Clover 採用 MoE 架構，總參數 350 億、每個 token 啟用約 30 億參數，支援思考模式。它的生成方式是「塊擴散」：把待生成內容切成若干塊，塊與塊依次推進，塊內的多個位置則並行更新、相互參考，一輪計算就有機會推動多個位置的生成。

但擴散模型往往需要多輪去噪才能把結果定下來，輪數太少內容可能沒調整好，輪數太多運算開銷又上升；而程式碼和 Agent 任務的上下文會不斷變長，歷史資訊的存取效率也成了問題。Clover 的解法，是圍繞塊擴散重構了門控 Delta 網路（GDN）：已生成的上下文被壓縮進持續更新的狀態中,供後續步驟讀取；當前生成的塊則透過雙向注意力,讓塊內 token 互相參考。同時，歷史記憶的讀出被當成獨立的資訊單元，與當前 token 一起參與注意力計算,讓模型自己學習如何權衡前文與當下內容，再搭配可學習的塊大小校準，減少塊變大後歷史資訊被稀釋的問題。

📊 WindTunnel 評測中速度快逾一倍、成功率也略勝一籌

在網頁 Agent 評測 WindTunnel 的 49 個任務中，每個任務嘗試 3 次，Clover 的中位執行時間為 1.52 秒，Jev＋Mercury 2.5 組合為 3.21 秒，用時少了一半以上；嘗試成功率分別為 98.6% 與 95.9%，Clover 也略高一些。官方演示中，Clover 透過 WebMCP 連續處理六項任務（開票、課程報名、金額彙總、活動狀態查詢、客戶資訊查詢、發票資訊查詢），執行速度明顯甩開 Gemini 3.6 Flash；在線上購物場景中，也能找到指定款式、顏色、尺碼的 T 恤並完成加入購物車、填寫訪客資訊、結帳的完整流程。

工具使用相關評測中，Clover 在 τ³ Overall 拿到 65.3、BFCL-v4 拿到 67.9；程式碼能力方面，SWE-bench Verified 拿到 73.6，Terminal-Bench 2.1 拿到 51.7。

⚠️ 擴散模型做 Agent 的老問題：格式出錯、卡在原地打轉

團隊坦言，擴散語言模型過去在 Agent 任務上的表現並不穩定：模型呼叫工具的格式可能出錯，也容易在同一步驟上反覆嘗試,沒能根據回傳結果調整動作。Clover 這次的進步正是體現在連續操作的穩定性上，但這也說明了這類模型要真正頂替自迴歸模型，仍需要持續驗證長程任務的穩定性。

🎯 關注擴散式 Agent 的延展路線

對正在評估 Agent 基礎設施延遲瓶頸的工程師而言，擴散語言模型的並行生成特性值得留意；團隊表示後續會推出多模態版本，並與合作方 Acrab 一起推進端側場景的系統適配與軟硬體協同驗證，同時探索更大規模模型與推理最佳化、量化部署。
