📌 免選規格：Lakebase Postgres 如何自動擴縮

TL;DR：Lakebase Postgres 靠 CPU、記憶體、工作集三訊號，即時自動調整運算規格。

先評估流量、抓一個「夠大」的資料庫規格，然後一路浪費運算資源到系統退役——Databricks 在這篇文章裡直接說，這個做法是過時的建築模式，尤其在運算資源本身變得昂貴的當下。

🤔 先選規格，是一個該被淘汰的舊習慣

傳統 Postgres 是綁在單一機器與磁碟上的有狀態行程，換機器或調整大小是需要停機的資料庫操作，因為機器同時擁有「執行」與「持久狀態」兩種責任。Lakebase Postgres 把這兩個責任拆開：運算節點可以啟動、停止、搬移、改變大小，而不需要搬動底下的資料庫。這是自動擴縮得以實現的基礎。

🧩 決定「何時」擴縮：三個訊號各出一個目標值，取最大者

三個訊號各自產生一個目標運算大小，最終擴縮目標取三者中最大值，並限制在使用者設定的最小／最大運算規格之間。

CPU 訊號最直接：用一分鐘平均值濾除短暫波動，再以五秒輪詢頻率更新目標。

記憶體訊號的失敗模式與 CPU 不同——CPU 吃緊只會讓查詢變慢，但 Postgres 一旦配置的記憶體超過 VM 上限，核心會直接砍掉行程，所以系統需要比 CPU 更快的訊號。做法是以兩種頻率監看記憶體，目標是把使用率壓在配置 RAM 的 75% 以下，保留給客體作業系統與其他行程的空間；vm-monitor 在每次提議縮減前都會檢查，若縮減後行程沒有足夠空間就不會執行。文中提到，這個輪詢式設計取代了原本依賴 cgroup memory.high 事件的作法，因為跨越 memory.high 會觸發 Linux 的回收與節流，輪詢反而更可預期、更穩定，同時仍能維持對 Postgres 記憶體約 100 毫秒等級的即時視角。

工作集（working set）訊號是全文最有意思的部分。Lakebase Postgres 把儲存與運算分離：頁面不在本地時，運算節點會向 pageserver 請求，取回的頁面快取在 compute cache（原稱 Local File Cache／LFC）裡，這是 Postgres shared buffers 的可調整延伸。許多 OLTP 工作負載一旦工作集完全放進本地記憶體，效能就會出現明顯轉折——但這正是純 CPU 訊號的盲點：快取未命中時查詢卡在等待網路回應，CPU 使用率反而偏低，恰好是最需要擴大快取的時刻。

💡 用「加時間戳記的 HyperLogLog」估計「現在」的工作集

為了直接估計工作集大小，系統採用 HyperLogLog——一種用固定小狀態估計集合基數的機率演算法。但標準 HyperLogLog 只會單調成長，暫存器一旦被某個雜湊值標記，就無法得知是何時、被誰標記，因此只能回答「這個運算節點從啟動以來總共存取過多少不同頁面」，卻答不出自動擴縮真正需要的問題：「當下這個工作負載涉及多少頁面」。沒有時間邊界，舊的匯入作業或分析查詢會一直留在估計值裡，讓運算規格長期偏大。

Lakebase Postgres 的做法是修改暫存器內容：不是設一個位元，而是在該位置寫入目前的時間戳記。要估計「從時間 T 以來」的基數，只要把 T 之後更新過的位置視為「已設定」、更早的視為「未設定」即可，這樣就能對任何以現在為終點的時間窗做估計。

📊 每 20 秒重算一次，尋找工作集的「跳躍點」

autoscaler-agent 每 20 秒針對 1 分鐘到 60 分鐘的多個時間窗蒐集工作集估計值。但沒有一個放諸四海皆準的窗口長度——太短會在工作負載結束後過度丟棄快取，太長則會為已經結束的工作繼續保留記憶體。演算法的解法是觀察工作集隨時間的變化型態：穩定工作負載的頁面估計值會先成長後打平；剛結束的高負載工作，一旦窗口拉長到涵蓋先前的負載，估計值就會出現跳躍。系統會尋找這個跳躍點，標記目前這段穩定期的起點；搜尋從 5 分鐘之後才開始，避免短暫停頓就讓規格立刻縮小、又要為下一波負載重新成長。若沒找到明顯跳躍，就採用 60 分鐘估計值，對應穩定工作負載整小時都活躍的情境。演算法最後還會把工作集成長「往前推算」，提前配置足夠的快取容量，避免較早讀入的頁面被較晚的頁面擠出、造成重複讀取。

🎯 實務啟示

對維運 Postgres 的工程師來說，這篇文章示範了「運算與儲存分離」如何把傳統上需要停機的 resize，變成純運算層級的動作；而用加上時間戳記的 HyperLogLog 去估計「當下」而非「累計」的基數，是一個值得參考的模式——當你需要對時間窗內的基數做估計、又不想耗費大量記憶體逐一計數時，這個變體是個輕量解法。
