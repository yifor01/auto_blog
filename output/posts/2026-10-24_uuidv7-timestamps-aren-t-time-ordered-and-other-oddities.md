📌 UUIDv7 的三個「其實沒有」:時間戳不可靠、單調遞增不成立、不可預測性也破功

TL;DR：UUIDv7 唯一能嚴格保證的屬性只有唯一性,其餘宣稱的優點在特定條件下都會失效。

多數介紹 UUIDv7 的文章都會吹捧它三大優點:ID 會單調遞增、帶有建立時間的時間戳、而且難以被猜測。但這篇技術分析指出,RFC 9562 本身就允許實作打破這些承諾,而某些符合規範的實作甚至會把這些屬性破壞到極端程度。

🤔 **問題出在哪**

作者指出,UUIDv7 真正嚴格成立的屬性只有唯一性與碰撞抵抗力,時間戳準確性、ID 排序、不可猜測性全都只是「大致上」而非「保證」。

🧩 **時間戳未必等於建立時間**

Postgres 文件在 `uuid_extract_timestamp` 的說明中就提醒,解出來的時間戳「未必精確等於 UUID 產生的時間」。RFC 9562 §6.1、§6.2 明確寫著實作「可以」更改時間戳欄位,甚至「可以讓時間戳超前實際時間」。

文中以 Python 標準函式庫的 `uuid.uuid7()` 為例示範這個問題:當計數器欄位溢位時,實作會遞增時間戳。但如果系統時鐘往回跳,且當下的產生負載超過每毫秒一個 ID,產生器就會陷入遞增循環,導致內嵌時間戳與真實時間的差距不斷擴大而非收斂。作者實測把時鐘往前調一小時後的輸出:

```
Initial delta: -0.000748
Set clock back one hour
New delta: 3695.277581
New delta: 3795.042411
New delta: 3894.80756
New delta: 3994.573106
```

理論上差距應該收斂回 3600 秒(一小時)並隨系統時鐘追上而縮小,但實際上差距持續擴大且無上限。相關的 Python 開發者討論串則認為,這個行為「符合 RFC」、「和其他實作一致」,而且在「本質上有缺陷的系統」上「沒有太多辦法」解決。

🧩 **單調遞增:1970 年代就已證明不可能**

作者提到跨節點的事件嚴格依時間戳排序,早在 1970 年代就被證明不可能達成,這也是向量時鐘(vector clock)等技術誕生的原因,根本原因在於系統時鐘無法同步到足夠的精確度。即使在單一節點、單一實作上,只要實作採用「毫秒時間戳不搭配計數器」的方式,也能輕易在一個簡單的 for 迴圈中就產生出亂序的 ID。換言之,RFC 規範本身並不保證嚴格單調遞增,不同實作(是否使用次毫秒精度時間戳、計數器、時鐘同步狀況)表現各異。

🧩 **時間戳洩漏與重啟後的亂序問題**

把時間戳嵌進 ID 裡,意味著分享 ID 時也同時分享了高精度的建立時間,例如使用者頁面網址中的 UUIDv7 可能洩漏帳號建立時間,即便頁面本身沒有顯示這項資訊。作者認為這類問題在多數安全評估中優先級都偏低,但在特定情境下仍值得留意。

另外,RFC 要求實作追蹤「上次使用的時間戳」以避免時間戳往回跳,但這必須把該時間戳寫入持久化儲存才能在程序重啟後仍然有效。作者檢視多個 UUIDv7 實作後,沒有找到任何一個會把時間戳寫入持久化儲存,代表只要系統時鐘往回跳、接著程序重啟,就會產生亂序的 ID。

⚠️ **這些問題有多嚴重**

作者的立場相對溫和:大致有序的 ID 仍然很有用,不建議因此把 UUIDv7 從系統裡拔掉,但工程師應該清楚自己實際依賴的假設是什麼,不要把「大致有序」當成「嚴格單調」來設計系統。

🎯 **實務啟示**

如果你的系統依賴 UUIDv7 作為主索引鍵來獲得「依建立時間排序」的免費效果,務必確認:你使用的語言/函式庫實作是否有計數器欄位、時鐘往回跳與程序重啟的組合是否可能發生在你的部署環境中。對需要嚴格事件順序的場景(如審計日誌、事件溯源),不要單純信任 UUIDv7 的時間戳,應搭配額外的邏輯時鐘或資料庫層的建立時間欄位做二次保障。
