📌 【Anthropic 官方實戰指南】電商 AI 智慧體別急著拆子智慧體，先問自己：這個指令一輪對話用幾次？

TL;DR：Anthropic 彙整電商客戶的實戰經驗，主張單一智慧體＋技能勝過子智慧體架構，並給出延遲與快取的具體優化槓桿。

當你的電商 AI 智慧體要同時處理商品搜尋、購物車、退貨、庫存查詢時，多數團隊的第一直覺是「每個業務領域配一個子智慧體」。但 Anthropic 在與零售、電商、旅遊、電信等產業客戶合作一年後發現，這個直覺往往是錯的。

🤔 電商 AI 智慧體，到底在解決什麼問題

文章將電商 AI 智慧體定義為「能簡化整個線上商品目錄買賣過程的智慧體」。面向消費者的版本負責搜尋商品、比價、找替代品、整理成訂單；面向商家的版本則回答銷售數據問題、執行促銷活動、管理庫存與定價。核心架構很單純：把 Claude 放進一個標準的智慧體迴圈（Agent Loop）中，圍繞目標推理、透過工具行動、透過技能學會操作流程，直到完成任務。前端沒有意圖路由器切分對話，後端也沒有一堆特定領域的子智慧體。

🧩 為什麼「單一智慧體＋技能」勝過子智慧體

電商對話通常橫跨多個意圖與輪次，需要共享大量上下文。在子智慧體架構中，每次把任務交接出去，都是一次「狀態丟失」的操作：購物車資訊、暫存修改、使用者偏好可能因交接而流失，還會多花好幾倍 Token、多等好幾秒延遲。業務領域也很難乾淨切割，例如退貨流程同時牽涉訂單歷史、購物車與商品目錄。

Anthropic 在多個企業級部署的對比測試中發現，單一智慧體加技能的架構，品質上持續優於「全部塞進一個提示詞」和「子智慧體」這兩種設計，且成本更低、延遲更小。子智慧體真正適合的場合，是主協調器把它當工具呼叫、處理高度垂直且自成一體的任務，例如需要大量搜尋文件、寫程式碼、遍歷資料模型的「深度研究」子智慧體；或是某個業務領域（如藥局、金融服務）本就有獨立合規要求的專屬智慧體，這種情況下應該直接「交接」對話所有權，而不是來回「委派」。

🧩 系統提示詞放什麼、技能放什麼：看使用頻率

判斷準則很直白：智慧體大多數輪次都會用到的資訊放進系統提示詞，因為載入一項技能會多耗掉一輪對話週期；長尾需求則做成技能。文章給出的經驗法則是，凡是涉及三分之一以上流量的指令都該寫進系統提示詞，安全與法律底線、品牌調性、使用者關鍵資訊（如過敏史）更是永遠留在提示詞裡。以參考實現為例，購物智慧體的提示詞包含背景設定、購物車與結帳規則、介面呈現規則和商品搜尋，其餘搜尋發現、購買研究、目標規劃、客戶關懷、記憶與個性化都做成技能；商家智慧體同理，每個操作領域（業績洞察、目錄列表、庫存操作、定價促銷、行銷活動）各自一項技能。

🧩 工具與 UI 元件的工程設計

兩個關鍵原則：工具要建立在既有系統與業務邏輯之上，而不是讓大模型重新實現排序、庫存、促銷等已經打磨多年的邏輯；工具的返回結果就是上下文，只回傳模型推理需要的欄位，把圖片 URL 等雜訊丟掉，錯誤訊息也該寫成明確指示（例如「查詢庫存請務必包含商品 ID」）而不是乾巴巴的錯誤碼。

另一個容易被低估的細節是把 UI 元件也做成工具。多數電商回覆其實是商品輪播圖、行程單、座位圖這類具體元件，而不是散文。文章指出，用提示詞讓模型輸出自訂標籤再由客戶端解析的做法會隨規模擴大而失效：模型對自訂標記法不如原生工具呼叫熟練、標籤定義會讓提示詞越來越臃腫、歷史對話還會被存成只有自家解析器看得懂的格式。經得起考驗的模式是把每個 UI 元件做成一個工具（如 present_products、present_itinerary），伺服器驗證並豐富參數後發事件，客戶端渲染。這樣一來，畫面上正顯示什麼直接記錄在訊息陣列裡，使用者說「第一個酒店」時智慧體立刻知道在指什麼。

📊 延遲與成本：快取命中率做到 90-99%

任務完成延遲＝對話輪次 × （首字顯示時間＋工具處理時間），三個槓桿是減少輪次、加快工具、加快 Token 生成。減少輪次的做法包括提前載入使用者可能用到的頁面上下文、用更聰明的模型減少規劃步驟、引導模型並行呼叫互不依賴的工具。工具端可以在參數一輸出完畢就「急切地」分發呼叫，文章提到這個技巧曾把數秒等待縮短到幾百毫秒以內，Claude Agent SDK 預設就是這麼做。

感知延遲上，邊生成邊渲染 UI 元件、用簡短自然語言展示「正在查詢…」的進度提示，都能在總執行時間不變的情況下讓使用者覺得系統更快回應。

成本方面，提示詞快取是最大槓桿：讀取被快取的輸入 Token 成本只有全新讀取的十分之一，寫入快取雖有約 1.25 倍溢價，但只要字首被第二次使用就能賺回來。文章指出，最佳的電商部署案例快取命中率高達 90-99%，處理約 10 萬 Token 時讀取快取速度能快 1.5 到 2 倍。快取是按字首匹配的，因此請求內容可分成三個依變化頻率排序的區塊，其中全域區塊（系統提示詞與工具定義）在每次會話中完全相同，應在其末尾放置快取斷點。

🎯 實務啟示

如果你正在為電商或其他消費者場景設計智慧體，先別急著拆子智慧體：把長尾功能做成技能、高頻指令留在系統提示詞，並把每個 UI 元件做成工具而非自訂標籤，往往能同時省下 Token、降低延遲、提升品質。至於延遲優化，先量測你的真實流量分布（多少輪次完成任務、快取命中率多高），再決定該選更聰明還是更快的模型。
