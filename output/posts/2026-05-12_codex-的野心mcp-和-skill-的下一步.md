📌 **Codex 的 Agent 生態野心**

你有沒有發現，頂尖的 AI Agent 介面長得越來越像？  
左邊會話、中間對話、右邊工作區——這不是巧合。  
當大家開始用 Agent 寫程式、做簡報，卻仍得跳出去微調時，一個更深層的需求正浮現。

🤔 **頂尖 Agent 應用不約而同收斂到三欄布局**

寶玉在密集使用 Codex App、Cursor、Claude 桌面版、TRAE SOLO 後觀察到：這幾款目前最頂尖的 Agent，在未協商的情況下，幾乎同時呈現左側專案與會話列表、中間與 Agent 對話、右側工作區的三欄結構。傳統聊天機器人只需要兩欄（會話歷史＋對話窗口），而 Agent 能自行執行編碼、檔案修改、工具調用之後，使用者必須檢視結果——因此右側工作區應運而生，用來放置檔案瀏覽、網頁預覽、變更審閱等功能。

🧪 **觀察方式：實際使用與版本更新紀錄**

這個結論來自於作者在數週內的實際操作體驗，以及注意到各產品在 4 月 16 日的大版本更新中，右側工作區的改動幅度最大。雖未進行受控實驗，但多款獨立產品的同步趨同提供了強烈的觀察依據。

🔑 **核心發現：三欄布局是當前 Agent 交互的近似最优解，但仍缺少「二次編輯」能力**

- 三欄布局滿足了 Agent 執行任務後的即時檢視需求。  
- 然而，使用者在 Agent 完成代碼、Markdown、PPTX 等產出後，常仍需要自行打開外部編輯器進行最後的微調。  
- 目前的右側工作區僅能預覽與審閱變更，無法直接編輯檔案，這意味著工作流程仍未實現「全程閉環」。

💡 **深入分析：MCP 與 Skill 只解決了「連接」與「怎麼做」的半塊拼圖，真正缺失的是使用者的二次編輯環節**

- Model Context Protocol (MCP) 讓 Agent 能透過統一規範連接工具、資料庫、日曆等，解決了「如何取得資源」問題。  
- Agent Skills 則讓 Agent 學會特定領域的知識與最佳實踐，解決了「如何完成任務」問題。  
- 但無論多強的 MCP 或多豐富的 Skill，若 Agent 無法讓使用者在同一介面上進行最後的手動潤飾，使用體驗仍會被迫中斷。  
- 作者指出，這正是近期 Markdown 編輯器與 Vibe Coding 相關工具再度受熱的原因——使用者渴望在 Agent 內部完成那最後 5% 的精準度。

🛠️ **研究限制：基於個人使用經驗的觀察，缺乏量化數據與長期追蹤**

- 結論主要來自作者個人使用與公開版本更新紀錄，未進行對照實驗或大規模用戶調查。  
- 未提供具體的使用時間、錯誤率或滿意度指標，因此無法量化三欄布局的優勢或二次編輯缺失的影響程度。  
- 對不同使用者習慣（例如偏好浮動面板而非 Tab 切換）的適應性亦未深入探討。

🎯 **實務啟示：把 Agent 打造成平台，透過插件機制與 Agent 版 App Store 來補足二次編輯與垂直領域能力**

- 參考 VSCode 與 Chrome 插件市場的成熟模式，讓社區開發者貢獻專業編輯器、設計工具、領域特定腳本等插件。  
- Agent 本身只需專注於任務調度與核心對話，將檔案預覽、二次編輯、垂直領域功能交給插件擴展。  
- 用戶可按需安裝：設計師裝設計插件、寫作者裝寫作插件，實現真正的「按需定制」。  
- 插件市場同時具備收費與版權保護機制，能為開發者提供持續打磨的動力，解決 Skill 難以商業化的問題——插件不像 Skill 那樣透明且易被複製，擁有較高的护城河潛力。  
- 這樣的生態不僅能讓 Codex 實現「Codex for (almost) everything」的願景，也將推動整個 Agent 產業從單一工具向平台化演進。
