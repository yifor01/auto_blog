📌 Claude 幫你審完一遍，人類才看：AI 時代的 Code Review 長這樣

TL;DR：AI 正把 code review 從終點把關變成即時拼字檢查。

以前的 code review 是一道關卡：寫完程式、開 PR、等同事有空看。現在這道關卡被拆散了，審查變成在你打字的同時就持續運作。

🤔 **從「人看過了嗎」到「什麼環節該由誰檢查」**

Claude Code 團隊的 Addy Osmani、Morgan Westlee Lunt 與 Qing Wang 在他們介紹團隊如何做 code review 的文章裡提到一個轉念：與其問「有沒有人讀過這段程式碼」，更精確的問題是「這個改動可能出什麼問題，該用哪一種檢查——自動化或人工——去抓住它」。這個問題一換，審查發生的時機也跟著變了：以前審查是寫完 code、開 PR 後的最後一道關；現在審查持續進行，更像是邊寫邊跑的拼字檢查。多數改動在人類被要求看之前，已經先被 Claude 審查並修正過至少一次，常見的例行錯誤在這個階段就被攔下，省下團隊注意力去處理更高層次的判斷與審視。

💡 **把規則寫進 pre-commit hook，而不是寫進文件**

另一則引言來自 Geoffrey Huntley，談的是同一個問題的另一面：怎麼讓 agent 真正遵守團隊的程式規範。他原本想靠更新 AGENTS.md 來告知 agent「請用我的診斷函式庫」，但文件和實際行為之間永遠有落差，而且會隨時間漂移。他的做法是寫一個 pre-commit hook，檢查 git diff 裡是否有直接呼叫可觀測性模組、跳過診斷函式庫的呼叫；一旦偵測到，就讓 commit 失敗，並注入提示告訴 agent 改用診斷函式庫。他形容這個做法效果立竿見影，「十分裡面變成十分」。

🎯 **實務啟示**

這兩段引言合起來指出同一個方向：與其靠文件或口頭約定去規範 agent 的行為，不如把規則做成會自動失敗的檢查點（像 pre-commit hook），讓 agent 在被擋下的那一刻直接收到修正指示；人力則保留給需要高層次判斷的審視，而不是逐行挑錯例行問題。
