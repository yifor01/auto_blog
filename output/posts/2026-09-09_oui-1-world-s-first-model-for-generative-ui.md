📌 全球首個生成式 UI 模型 OUI-1，消費級 GPU 就能跑

TL;DR：OUI-1 是專為即時生成介面設計的擴散語言模型，開源權重可在 RTX 5090 上運行。

多數人想像的「AI 生成介面」,是模型吐出一段 JSON 或程式碼再由前端渲染,速度和可靠性都難以達到「軟體」等級。OUI-1 想解決的正是這個落差:讓生成式介面快到像傳統軟體一樣即時,而且能在自家 GPU 上跑。

🤔 **代理驅動介面的三個硬限制**

團隊(OpenUI)認為,代理驅動的介面是軟體的未來,但要做到,必須同時滿足三個限制：生成速度要在一秒以內、可靠到能當作軟體使用、模型要小到能在消費級硬體上本地運行。他們先前的專案 AppLess 曾用 Gemma 4 搭配 Cerebras 雲端硬體探索這種體驗，但依賴特殊雲端硬體。要把這件事搬到裝置端，代表要在運算資源大幅縮減的情況下，仍維持回應速度、生成品質與正確性,OUI-1 就是解決這個問題的第一步。

🧩 **DiffusionGemma 加上專用語言 OpenUI Lang**

OUI-1 是一個微調自 DiffusionGemma 的 26BA4B 模型(FP8 下可在 RTX 5090 這類消費級 GPU 運行)，用來寫一套名為 openui-lang 的介面描述語言,權重已依 Gemma Terms of Use 條款上架 Hugging Face。

選擇這套組合有其道理:OpenUI Lang 相較 JSON 可省下高達 67% 的 token，且支援串流,介面能在模型還沒生成完就開始顯示。至於底層模型，一般自回歸模型一次只能生成一個 token，受限於記憶體頻寬；DiffusionGemma 則是擴散語言模型，能一次寫出 256 個 token 的區塊,從雜訊開始，一旦確定某個 token 就直接定案。據 Google 公布的數字，DiffusionGemma 在單顆 H100 上可達每秒超過 1,000 個 token，在 RTX 5090 上則超過每秒 700 個 token。

💡 **監督式微調反而讓模型變慢，直到自我蒸餾出現**

速度有了，接下來要解決的是可靠性。團隊發現，DiffusionGemma 原始版本在 Generative UI Benchmark 上只拿到 13.0%，介面經常出現「schema 錯誤」(如使用不存在的列舉值、缺少必要屬性、虛構元件)與「wiring 錯誤」(如定義了名稱卻沒使用、定義了區塊卻沒接回根節點)。

訓練分兩階段進行。第一階段是監督式微調:先用約 700 筆由更大模型撰寫、橫跨七種元件庫的 OpenUI Lang 範例，在單顆 A100 上做 LoRA 微調。結果 loss 雖然下降，基準分數卻同步下滑,因為模型學會寫更長、更密集的程式，但幾乎都無法乾淨解析。團隊把範圍縮小到基準測試所用的單一元件庫後，分數從 13.0% 提升到 28.8%，但代價是 schema 錯誤與 wiring 錯誤此消彼長,像翹翹板一樣,不同訓練回合中一種錯誤下降,另一種就上升(例如三次跑分別記錄到 schema/wiring 錯誤數為 78/66、112/40、51/65)，始終沒有一次同時把兩者都壓低。同時模型還變慢了:同樣 20 個簡短需求下,單次生成時間從 1.6 秒拉長到 4.3 秒,原因是微調後的模型會寫出真實的名稱與數值(平均每敘述 32 個 token),而非基礎模型的簡短泛用輸出(平均 22 個 token)，需要約兩倍的去噪步驟才能定案每個 token。

轉折點出現在第二階段的自我蒸餾。團隊意識到 OpenUI Lang 有一個可驗證的獎勵訊號:parser 能明確判斷一段介面是否結構有效，並指出具體的 schema 或 wiring 錯誤,這代表模型可以自己當自己的老師。具體做法是拒絕採樣搭配修復的自我訓練:模型寫出數百個 OpenUI Lang 程式,parser 保留通過的部分;接近正確但有瑕疵的程式會經過修復流程，只修正 parser 回報的具體缺陷(中位數只改動一個敘述句,且拒絕任何重寫或憑空杜撰的修改)；再由一個裁判模型檢查每份存活下來的程式是否符合原始需求。這些存活範例成為下一輪的訓練資料(每輪 500 步，在單顆 A100 上約需一到兩小時)，如此循環。

📊 **分數翻倍到 57.1%，兩類錯誤同時下降**

自我蒸餾之後，速度重新回升:同樣 20 個簡短需求下，單次生成時間從 4.3 秒降到 1.9 秒，即使輸出的 token 數比原始 DiffusionGemma 多出 28%。更關鍵的是,翹翹板效應消失了:基準分數來到 57.1%，schema 錯誤從 292 降到 76，wiring 錯誤從 971 降到 484，兩類錯誤第一次同時下降。另外一組統計顯示,每 100 個敘述句的缺陷數,從 DiffusionGemma 的 35.3、監督微調後的 16.4，一路降到 OUI-1 的 3.8，減少了 13.8 倍。團隊未證實的假設是:用模型自己生成的文字訓練,能讓 loss 在大部分地方維持很低,梯度因此集中在少數真正改變的地方(被修復的敘述句、被推向眾數的採樣選擇)，前者教會模型修正 wiring,後者則讓熵界能更早定案每個 token。整套流程後續也被複製到全部 27 種元件庫上。

⚠️ **仍是特定語言與元件庫上的成果**

目前公開的結果集中在 OpenUI Lang 這套自有描述語言與其對應的元件庫體系，並依賴 FP8 精度與 RTX 5090 這類特定硬體設定，實際換到其他框架、其他硬體時的表現,素材中並未提及。

🎯 **實務啟示**

對於想在本地或邊緣裝置上做生成式 UI 或結構化輸出的團隊，OUI-1 的訓練過程提供一個可參考的路徑:當任務有明確、可自動驗證的正確性訊號(如 parser、compiler)，用拒絕採樣加自我蒸餾去強化模型，往往比單純堆更多監督式資料更有效,還能同時解決品質與速度兩個看似互斥的目標。
