📌 本地小模型實戰：不靠雲端 API 也能做 AI 專案

TL;DR：1B–13B 參數的小型語言模型已成熟到能在筆電本地執行，兼顧隱私、成本與延遲，本文整理從選型到部署的實務流程。

雲端 API 的預設心態很久沒被挑戰過：模型越大越好，延遲、用量費用和資料外流都是不得不接受的代價。但這個假設已經不再成立。1B 到 13B 參數的小型語言模型（SLM）小到能在一般筆電或單張消費級 GPU 上執行，卻已經能處理相當廣泛的實務任務。

🤔 **為什麼要把模型搬回本地**

隱私與資料掌控是最直接的優勢：模型在自己的機器上執行,提示詞和輸出都不會離開你的環境,這對處理敏感文件、專有商業資料或個人資訊的應用尤其重要,雲端 API 不論隱私政策寫得多好,都等於在推論流程裡引入了第三方。成本可預測性是另一個優勢：API 費用隨用量成長,本地模型則是固定的硬體成本,不用按 token 計費,可以更自由地做原型驗證,也更容易在不盯著預算的情況下擴展內部工具。延遲也常被低估:本地推論完全省去網路來回,對於回應速度會影響體驗的互動式應用,即使硬體只是中階規格,本地推論也能感覺明顯更快。當然權衡也是真實的:本地模型的內容視窗通常較小,在複雜任務上的原始能力較低,還需要一些初期設定,以及能撐得住模型的硬體。一個 70 億參數的模型在 4-bit 量化下,大約需要 8 GB 的 VRAM 或 RAM 才能以合理速度執行。

🧩 **怎麼選對的模型：參數量、任務專精與量化格式**

參數量和硬體是綁在一起的:1 到 30 億參數的模型幾乎在任何配有 8 GB RAM 的現代機器上都能跑;70 億參數是最受歡迎的量級,在消費級硬體上的品質與效能取得不錯的平衡;130 億參數則已經逼近單張高階 GPU 或大記憶體機器能妥善處理的極限。任務專精同樣重要,有些模型專門針對程式碼微調,例如 Code Llama 或 Qwen-Coder,有些則更適合指令遵循、摘要或對話任務,與其預設選能跑得動的最大模型,不如先把模型和任務對齊。量化格式則影響檔案大小與推論速度,多數本地執行的模型以 GGUF 格式發佈,可以量化到 4-bit 或 8-bit 精度,以有限的品質代價換取更低的記憶體需求,對多數實務應用而言,Q4 或 Q5 量化是不錯的預設選擇。值得評估的熱門模型家族包括 Llama 3、Mistral、Gemma 2、Phi-3 與 Qwen 2.5,各有不同強項,但最有意義的評估方式,還是拿候選模型直接跑你自己的任務,檢查輸出是否達到你的品質標準。

🧩 **用 Ollama 把模型跑起來並調校**

選定候選模型後,需要一個執行方式。Ollama 目前是最容易上手的本地語言模型執行工具,處理模型下載、GPU 加速,並透過簡單的命令列介面提供本地 API 端點,支援 macOS、Linux 與 Windows。安裝完成後,下載並執行一個模型只要一行指令,Ollama 預設會在 11434 埠透過本地 REST API 提供服務,代表應用程式碼可以用呼叫一般 HTTP API 的方式與它互動,LangChain 和 LlamaIndex 都原生支援 Ollama 整合,能直接把本地模型接進既有的應用架構。除了 Ollama 內建的模型庫,也可以直接從 Hugging Face 拉取 GGUF 格式的模型透過 Ollama 執行,開啟更廣的選擇範圍,包括社群微調版本。跑起來之後,還需要針對自己的使用情境調校:Ollama 用 Modelfile 定義模型行為,概念上類似 Dockerfile,但用來設定語言模型,可以調整系統提示、設定內容視窗長度、修改溫度與取樣參數、定義停止或格式限制。內容視窗大小值得特別留意,多數模型支援 4K 到 32K token 的內容視窗,但更大的視窗會佔用等比例更多的記憶體,若應用只需要處理短提示與回應,縮小內容視窗能同時改善速度與記憶體使用。溫度控制輸出的隨機性,對程式碼生成或資料擷取這類需要一致性與準確度的任務,較低的溫度值(0.1 到 0.3)會產生更確定的輸出;對創意寫作或腦力激盪類應用,較高的值(0.7 到 1.0)則會產生更多變化的回應。系統提示則是輸出品質很大一部分的來源,一個明確定義模型角色、預期輸出格式與應遵守限制的系統提示,能大幅拉近通用模型和專用工具之間的差距,花時間打磨系統提示,往往比換更大的模型更划算。

🎯 **實務啟示**

文件問答是最實際的起點之一:把本地 SLM 和檢索系統結合,就能建出一套針對自己的檔案、PDF、筆記或內部文件回答問題的流程,且資料完全不離開本機。對工程師來說,這篇文章的重點不是「SLM 能取代雲端大模型」,而是提醒:在動手接雲端 API 之前,先把任務丟給一個本地小模型加上一份用心寫的系統提示試試看,很多時候差距沒有想像中大。
