📌 「Prompt 根本不是一個東西」：一位資深工程師的 Agent 生產化血淚筆記

TL;DR：25 年資歷工程師分享用 pass^k 測試與自動化 prompt 優化，取代手動寫死指令的生產經驗。

如果你以為把 prompt 寫好、交給團隊各自維護一段負責自己領域的指令，Agent 就能穩定運作，這篇來自 Hacker News 的第一手經驗談會讓你重新思考。

🤔 **模型失控的方式，往往簡單到令人意外**

作者是一位在洛杉磯工作、擁有約 25 年經驗的工程師，近期投入讓消費者導向的 Agent（區別於主觀輸出的聊天機器人）在正式環境中可靠運作。他觀察到一個現象：即使是最聰明的模型，在要求結構化輸出時仍會有一小部分請求徹底失控。例如要求模型回傳「80 字元以內的標題」，多數時候沒問題，但偶爾會整個欄位被灌爆成一串無意義文字。他描述某次追查後發現，內容其實是模型反覆對自己碎念關於 JSON 格式的「筆記」；而解法竟然只是把欄位名稱從「title」改成「heading」就修好了 —— 一個他自己都形容「完全脫序」（deranged）的修法，且不保證未來不會再壞掉。

業界用來對付這種「一小部分請求失控」問題的做法，是重複大量執行同一測試，術語稱為 pass^k（pass power k），藉此在問題被使用者踩到之前先自己發現。

🧩 **核心論點：Prompt 不是可以獨立存在、隨插即用的東西**

作者提出一個反直覺的主張：多數人以為的「prompt 很重要」，其實理解方式是錯的。把一段新的 prompt 加進 Agent，等於是把它丟進一個完全不同的上下文環境，跟原本測試時的環境不同；既有的大量其他指令一定會影響新 prompt 的表現，而且通常是往壞的方向影響。Agent 原本就有一堆你希望它繼續維持的行為，新加入的上下文可能會打亂這些行為；更麻煩的是，Agent 本身也會隨時間演進，模型甚至可能因為未知原因自己改變行為模式。

因此，「品牌語氣（voice）團隊自己維護語氣相關 prompt」這種常見分工模式，作者認為在規模化時是錯誤的模式（甚至說「連錯都稱不上」）——因為 prompt 從來就不是一個可以獨立測試、獨立交付的單元。

🧩 **實際做法：讓 Claude 生成對抗性測試，再用 GEPA 自動優化**

作者分享了他目前採用的流程：先讓 Claude 讀過既有的 skill／prompt，接著要求它生成大量對抗性情境（模擬惡意使用者試圖繞過規則）以及可能被新 prompt 意外破壞的良性情境，並把這些情境全部轉換成 pass^k 測試。接著分別在「有無新 prompt」的情況下跑這些測試，理想情況下新的 prompt 能讓測試表現往好的方向移動，但作者也坦言並非總是如此——有時模型本來就已經做得不錯，或是比預期更抗拒被特定方式引導。

當手動調整不夠用時，下一步是把 prompt 接上一個最佳化演算法，作者以 GEPA（genetic pareto）為例：這是一套內建 LLM 的演算法，能針對測試套件的結果反思 prompt 表現好壞的原因，並自動嘗試修改，如此反覆迭代直到收斂出一個「最佳化」版本的 prompt。最終得到的 prompt 內容，可能跟一開始的版本長得完全不一樣。

⚠️ **小心優化器只是在背測試題**

作者特別提醒，跑完優化流程後，必須確認優化器沒有「作弊」——也就是把測試案例中的具體例子直接硬編碼進 prompt 裡，造成表面上分數變好、實際上只是過擬合（overfit）了你手上的測試集。

🎯 **實務啟示**

對正在把 Agent 推向生產環境的工程師來說，這篇文章傳達的訊息很直接：不要把 prompt 當成獨立、可插拔的模組來管理，而要把它當成一個需要跟整體上下文、既有指令、模型版本共同測試的系統。與其靠人力反覆手動調 prompt，不如建立一套可重複執行的 pass^k 測試，再考慮接上自動化 prompt 優化流程，但務必留意過擬合的風險。
